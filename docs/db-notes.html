1. 事务 · 要么全成，要么当作没发生过

形象比喻

转账不是一个动作，是两个动作：从我这儿扣、往你那儿加。如果中间断电了，钱就凭空消失了。事务的作用就是给这两个动作套一个信封 —— 信封要么整个寄到，要么当作从来没寄过，绝不允许「寄了一半」。

1.1 ACID 四个字分别在保证什么

保证什么靠什么实现（InnoDB）
A 原子性一组操作要么全做，要么全不做undo log（记录「怎么撤销」）
C 一致性数据始终满足业务约束（如账目总额不变）其余三个 + 应用层约束共同达成，它是目的不是手段
I 隔离性并发事务之间不互相干扰锁 + MVCC
D 持久性提交了就不会因为宕机而丢redo log（先写日志再写数据页）
面试常见追问

「ACID 里哪个最特殊？」答 C（一致性）：它和另外三个不是一个层次的东西。A、I、D 是数据库提供的手段，C 是这些手段要达成的目标，而且相当一部分一致性（比如「持仓不能为负」）数据库根本不知道，得靠业务代码和约束自己保证。

1.2 交易系统里的实际用法

START TRANSACTION;

UPDATE account SET balance = balance - 100 WHERE id = 1 AND balance >= 100;
-- 检查影响行数：如果是 0，说明余额不足，要主动 ROLLBACK
UPDATE account SET balance = balance + 100 WHERE id = 2;
INSERT INTO transfer_log (from_id, to_id, amount) VALUES (1, 2, 100);

COMMIT;
易踩坑

把余额判断写成先 SELECT 再 UPDATE，两条语句之间别人可能已经把钱花掉了。正确做法是把条件写进 UPDATE 的 WHERE 里，然后检查影响行数 —— 这样判断和扣减是同一个原子操作。

2. 隔离级别 · 并发下会读出什么怪东西

如果事务之间完全不隔离，会读到三类越来越隐蔽的怪现象。先看清这三个现象，隔离级别的设计动机就自然明白了。

2.1 四个隔离级别

级别脏读不可重复读幻读说明
读未提交 RU会会会基本不用
读已提交 RC不会会会Oracle / PostgreSQL 默认，互联网业务常用
可重复读 RR不会不会InnoDB 下基本不会MySQL 默认
串行化不会不会不会相当于全部串行，吞吐极低
这里最容易答错

SQL 标准说「可重复读仍然可能幻读」，但 InnoDB 的可重复读用间隙锁把幻读基本挡住了。所以标准答案是分两层说：按 SQL 标准 RR 不解决幻读；但在 InnoDB 的实现里，快照读靠 MVCC、当前读靠间隙锁，两条路都堵上了。能主动区分「标准」和「实现」，这题就答满了。

3. MVCC · 为什么读数据不用排队

形象比喻

如果读也要加锁，那一个人在改数据时所有人都得干等着，数据库就没法用了。MVCC 的思路是：每次修改都不覆盖旧值，而是留一份旧版本。就像文档的历史版本，改的人在写新版，读的人照样看自己进来时那一版 —— 读和写互不打扰。

3.1 快照读 vs 当前读（高频考点）

快照读当前读
语句普通 SELECTSELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE / INSERT
读到什么ReadView 对应的历史版本最新已提交版本
加锁吗不加锁加锁（行锁，可能带间隙锁）
为什么要有读写不阻塞，吞吐高要改数据，就必须基于最新值，否则会覆盖别人的修改
经典陷阱题

同一个事务里先普通 SELECT 读到 100，然后执行 UPDATE account SET balance = balance + 1，再 SELECT，会读到多少？答案是基于最新值加 1 的结果，因为 UPDATE 是当前读，它看到的是别人已提交的最新值，不是你之前那张快照。快照只管住普通读，管不住写。

4. 锁 · 行锁、间隙锁与死锁

4.1 间隙锁：锁的不只是行，还有行之间的「缝」

MVCC 能挡住快照读的幻读，但挡不住当前读 —— 你 FOR UPDATE 查出 3 行准备处理，别人插进来第 4 行，一样出问题。InnoDB 的解法是连缝隙一起锁上。

锁锁住什么什么时候出现
记录锁 Record Lock某一条已存在的索引记录等值命中唯一索引
间隙锁 Gap Lock两条记录之间的开区间，不含记录本身RR 级别下的范围查询
临键锁 Next-Key Lock记录 + 它前面的间隙，InnoDB 的默认行为RR 级别下的当前读
意向锁 IS / IX表级标记，表示「表里有行被锁了」自动加，用来让表锁快速判断冲突，不和行锁互斥
最要命的一条

行锁是加在索引上的，不是加在行上的。如果 WHERE 条件没走索引，InnoDB 只能逐行扫描并把扫过的每一行都锁上 —— 效果等同于锁全表。所以「更新语句没走索引」不只是慢，它会直接把并发打死。

5. 索引 · B+ 树为什么长成这样

形象比喻

没有索引就是一页页翻整本书找关键词；有索引就是先翻书后面的索引页，看到「第 328 页」再直接跳过去。索引的本质是：多存一份按顺序排好的目录，用空间和写入代价换查找速度。

5.1 为什么不用别的结构

结构为什么不合适
二叉搜索树 / 红黑树每个节点只有两个孩子，百万行数据树高二十多层，等于二十多次磁盘 IO
哈希索引等值查找确实是 O(1)，但不支持范围查询、不支持排序、不支持最左前缀
B 树非叶子节点也存数据，每页能放的键变少，树就变高；而且叶子没有链表，范围查询要回溯
一句话回答

「为什么用 B+ 树？」因为磁盘 IO 是按页读的，而且慢。B+ 树把非叶子节点做成纯目录，让一页能装下上千个键，从而把树压到三四层；数据全放叶子并用链表连起来，让范围查询变成顺序扫描。把「磁盘」这个前提说出来，这题就答到点子上了。

6. 聚簇索引与二级索引 · 回表和覆盖索引

InnoDB 里数据本身就存在主键索引的叶子上，这棵树叫聚簇索引。你在别的字段上建的索引叫二级索引，它的叶子存的不是数据，而是主键值。

为什么建议用自增主键

聚簇索引是按主键顺序排列的。自增主键意味着新行总是追加在最后，页写满了就开新页；而如果用 UUID 这类随机主键，新行会插到中间，导致页分裂和大量随机 IO，写入性能明显下降，索引也更占空间。

7. 联合索引 · 最左前缀就是字典排序

形象比喻

联合索引 (省, 市, 区) 就像通讯录先按省排、省相同再按市排、市也相同才按区排。所以「找浙江的」很快；「找浙江杭州的」也很快；但「找所有叫西湖区的」就没办法了 —— 因为区名在整本通讯录里是散乱的，你只能一页页翻。

怎么设计联合索引的列顺序

区分度高的、以及等值查询的列放前面，范围查询的列放最后。因为范围条件之后的列就用不上索引了：WHERE a = 1 AND b > 10 AND c = 5 这个查询里，c 是排不上用场的，索引只能用到 a 和 b。

8. 索引失效的典型场景

写法为什么用不上索引怎么改
WHERE DATE(t) = ?函数结果在索引里不是有序的改成对原字段的范围比较
WHERE id + 1 = 10同上，字段参与了运算改成 id = 9
WHERE name LIKE '%三'不知道开头就没法在有序目录里定位'三%' 可以用；确实要后模糊就上全文索引
WHERE phone = 13800000000（phone 是字符串）类型不匹配，会隐式把字段转成数字，等于套了函数参数加引号，保持类型一致
WHERE a = 1 OR b = 2b 上没索引时整条只能全表扫两列都建索引，或改写成 UNION
索引列区分度太低（如性别）命中一半的行，回表成本比全表扫还高优化器会主动放弃索引，这是对的
别背成死规则

网上流传的「索引失效十八条」里有不少是过时或有条件的。真正可靠的做法是：拿不准就 EXPLAIN 跑一遍。优化器是基于统计信息做成本估算的，同一条 SQL 在数据量变化后可能走完全不同的计划。

9. EXPLAIN 怎么读

面试里问「你怎么优化慢查询」，标准起手式就是 EXPLAIN。只需要重点看四列。

列看什么
type访问方式，最重要的一列。从好到坏：const → eq_ref → ref → range → index → ALL。看到 ALL 就是全表扫
key实际用了哪个索引。为 NULL 说明一个都没用上
rows预估要扫多少行。和最终返回行数差距越大，说明白扫的越多
ExtraUsing index = 覆盖索引，很好；Using where = 取回来再过滤；Using filesort / Using temporary = 需要额外排序或临时表，通常是要优化的信号
 
EXPLAIN SELECT id, amount FROM trade
        WHERE account_id = 1001 AND trade_time >= '2026-01-01'
        ORDER BY trade_time;

-- 理想结果：
--   type  = range
--   key   = idx_account_time        （联合索引 account_id + trade_time）
--   Extra = Using index             （要的列都在索引里，不用回表）
--   而且没有 Using filesort ——
--   因为索引本身就是按 trade_time 有序的，排序被顺带省掉了
优化慢查询的标准回答

① 先用慢查询日志定位到具体是哪条 SQL；② EXPLAIN 看是不是全表扫、有没有走对索引、有没有 filesort；③ 按最左前缀和覆盖索引的思路调整索引或改写 SQL；④ 再看是不是本身就返回了太多数据（该分页、该聚合、该拆分）；⑤ 改完再 EXPLAIN 和压测一次做对比。最后一步最容易被忘，但没有前后对比就说不清到底优化没优化。

10. redo / undo / binlog · 持久性从哪来

形象比喻

改数据时如果每次都去磁盘上把那一页找出来改掉，全是随机 IO，慢得没法用。所以数据库的做法是：先在本子上按顺序记一句「我要把某页改成什么样」，再慢慢把真正的页刷下去。这个本子就是 redo log，顺序写非常快。就算这时断电，重启后照着本子重做一遍就行。

WAL 和你写过的代码是同一个思路

Write-Ahead Logging 的核心是把随机写换成顺序写 —— 先顺序追加一条日志（快），再择机把真正的数据页批量刷到磁盘（慢但可以攒着做）。这和交易系统里「先落 journal 再更新内存态」、和 Linux 的 page cache 回写，是完全同一套思路。

11. 一页速记

问题一句话答案
ACID 靠什么实现原子性靠 undo、持久性靠 redo、隔离性靠锁和 MVCC，一致性是前三者要达成的目标
不可重复读 vs 幻读前者是同一行的值变了，后者是符合条件的行数变了
MySQL 默认隔离级别可重复读；Oracle 和 PostgreSQL 是读已提交
RR 解决幻读了吗标准说没有；InnoDB 里快照读靠 MVCC、当前读靠间隙锁，基本解决了
MVCC 是什么每行留多个版本串成链，读事务按进门时的 ReadView 找到该看的那版，读不加锁
快照读 vs 当前读普通 SELECT 读历史快照不加锁；增删改和 FOR UPDATE 读最新值并加锁
为什么用 B+ 树非叶子只存键 → 扇出大树矮 → 磁盘 IO 少；叶子成链表 → 范围查询快
什么是回表二级索引叶子只有主键，还要再查一次聚簇索引取整行；要的列都在索引里就叫覆盖索引
为什么用自增主键顺序追加，避免页分裂和随机 IO；主键短，所有二级索引也跟着省空间
最左前缀为什么存在联合索引是逐级排序的，跳过前面的列，后面那列在全局就是乱的
索引什么时候失效本质只有一条：你比较的东西不再是索引里排好序的那个东西
EXPLAIN 看什么type 别是 ALL、key 别是 NULL、Extra 别有 filesort 和 temporary
行锁加在哪加在索引上。没走索引就退化成锁住扫过的每一行，等于锁表
数据库死锁怎么办数据库会自动检测并回滚其中一个，应用层必须能重试；根治靠统一加锁顺序
redo / undo / binlogredo 管崩溃恢复、undo 管回滚和旧版本、binlog 管主从复制和备份
面试怎么讲最稳

这块的加分点不在于记住多少条结论，而在于能不能把机制讲成因果链。比如被问到索引，与其罗列失效场景，不如说：「索引是按字段原值排好序的目录，所以任何让比较对象不再是这个原值的写法 —— 函数、运算、隐式类型转换、前导模糊 —— 都会让有序性失去意义，也就用不上索引了。」一句话覆盖一整类问题，比背十八条更能说明你真懂。

1. 一分钟决策表：什么现象用什么工具

核心思路

调试最耗时的从来不是「用工具」，而是选错了工具。先把现象归类，工具自然就定了。

现象首选工具一句话理由
崩溃了，有 coregdb ./prog core现场已封存，直接进去看栈
崩溃了，没有 coredmesg + ulimit -c多半是被 kill -9 / OOM Killer 杀的
进程卡住不动pstack 或 gdb -p PID看所有线程停在哪一行，死锁一眼看穿
内存持续增长ASan / massif / heaptrack / pmap先区分「真泄漏」还是「池不还给 OS」
越界 / 野指针 / use-after-freeASan（-fsanitize=address）崩在第一现场，而不是很久之后
偶现的数据错乱TSan（-fsanitize=thread）数据竞争靠肉眼几乎查不出来
CPU 打满perf top → perf record + 火焰图直接定位到最烫的那个函数
慢，但 CPU 不高strace -T / 查锁与 IO时间花在等待上，不在计算上
行为诡异（读错文件、权限问题）strace -f系统调用不会撒谎
网络连不上 / 连接堆积ss -tanp / tcpdump先看状态机，再看包
加载了错误版本的库ldd / /proc/PID/maps确认实际加载路径
只有崩溃地址，没有符号addr2line / c++filt把地址翻回文件行号

2. gdb 基础：启动、断点、栈、变量

2.1 四种启动方式

gdb ./prog                    # 从头调试
gdb --args ./prog -p 8080     # 带命令行参数（★ 比进去再 set args 方便）
gdb ./prog core.1234          # 事后分析 core
gdb -p 1234                   # attach 到【正在运行】的进程（生产排障主力）
attach 注意

gdb -p 会暂停整个进程，生产环境上要快进快出，看完立刻 detach（不要 quit，quit 在某些情况下会杀掉进程）。若提示权限不足：echo 0 > /proc/sys/kernel/yama/ptrace_scope。

2.2 运行控制

命令简写作用
runr开始运行
start—运行并停在 main 第一行
continuec继续跑到下一个断点
nextn单步，跳过函数调用
steps单步，进入函数
finish—跑完当前函数并打印返回值（很实用）
until Nu跑到第 N 行，用来跳出循环
return—强制立刻返回（可指定返回值）
advance 位置—跑到指定位置，不用设断点

2.3 断点

break order.cpp:120         # 文件:行号
break OrderBook::insert     # 函数名
break *0x4005d6             # 地址
tbreak main                 # 一次性断点，命中后自动删除
rbreak ^Order::             # 正则批量下断点

info breakpoints            # 列出所有断点（缩写 i b）
delete 2                    # 删第 2 个
disable 2 / enable 2        # 临时禁用/启用
condition 2 id == 1001      # 给已有断点补条件
最实用的两个技巧

① 条件断点：循环跑一百万次，你只关心某一次。

break process if orderId == 88888
break vec.cpp:42 if i > 10000 && ptr == nullptr

② ignore 跳过前 N 次：不知道条件怎么写，但知道大概第几次出问题。

ignore 1 5000      # 第 1 号断点，前 5000 次不停

2.4 观察点 watchpoint —— 「到底是谁改了我的变量」

这是 gdb 最被低估的功能。变量莫名其妙变成了脏值，用它一步到位：

watch  g_counter        # 值【被修改】时停下，并打印【改前改后】的值
rwatch g_counter        # 被【读取】时停下
awatch g_counter        # 读或写都停

watch -l ptr->field     # -l 锁定当前地址，避免 ptr 变了跟丢
info watchpoints
限制

硬件观察点通常只有 4 个（受 CPU 调试寄存器限制），且只能监视固定长度的内存。超了会退化成软件观察点，速度慢上百倍。另外变量出作用域后观察点会自动失效。

2.5 栈与变量

bt                    # 调用栈（最常用的第一条命令）
bt full               # 每一帧都带局部变量
bt 10                 # 只看最近 10 帧（栈很深时）
frame 3               # 切到第 3 帧
up / down             # 上下移动一帧

info locals           # 当前帧的局部变量
info args             # 参数
info registers        # 寄存器

p order               # 打印变量
p *ptr                # 解引用
p *arr@10             # ★ 打印数组前 10 个元素
p/x flags             # 十六进制（/t 二进制 /d 十进制 /c 字符）
p obj.method()        # 甚至可以调用函数
ptype Order           # 看类型定义
whatis x              # 看变量类型

x/16xb ptr            # 按字节 dump 内存
x/4dw ptr             # 按 4 字节整数
x/s charPtr           # 当字符串
x/5i $pc              # 反汇编当前位置的 5 条指令
调试期改状态 
set var retryCount = 0      # 直接改变量，验证「如果这里是 0 会怎样」
call reloadConfig()         # 运行中调用函数
display orderCount          # 每次停下自动打印这个表达式

2.6 多线程

info threads              # 列出所有线程，* 标记当前线程
thread 3                  # 切到 3 号线程
thread apply all bt       # ★★ 所有线程的调用栈 —— 死锁排查第一命令
thread apply all bt full

set scheduler-locking on  # 单步时【冻结其他线程】，避免它们跑飞
set scheduler-locking off # 默认值，恢复

3. gdb 高级技巧

3.1 断点命中后自动执行动作（不用手动敲）

break handleOrder
commands
  silent            # 不打印"Breakpoint 1, ..."的噪音
  printf "id=%d price=%f\n", order.id, order.price
  continue          # 打印完自动继续
end

相当于不改代码就插了一行日志 —— 生产环境不方便重新编译时特别有用。

3.2 抓异常和 abort

catch throw           # C++ 异常【抛出】的那一刻停下（能看到抛出点的栈！）
catch catch           # 被捕获时停
break abort           # assert 失败 / 未捕获异常最终走到这里
break __cxa_throw     # 等价于 catch throw
catch syscall write   # 特定系统调用

catch throw 非常关键：普通调试只能看到 catch 块里的栈，那时**真正的抛出现场已经被栈展开销毁了**。

3.3 打印 STL 容器

GDB 7 之后自带 Python pretty-printer，p myVector 应该直接显示 {1, 2, 3} 而不是一堆内部指针。如果没生效：

# ~/.gdbinit
python
import sys
sys.path.insert(0, '/usr/share/gcc/python')
from libstdcxx.v6.printers import register_libstdcxx_printers
register_libstdcxx_printers(None)
end

临时绕过：p *v._M_impl._M_start@v.size()（对 libstdc++ 的 vector）。

3.4 一份好用的 .gdbinit

set print pretty on           # 结构体分行显示
set print object on           # 按【实际】类型而非声明类型打印多态对象
set print static-members off  # 少点噪音
set print elements 200        # 数组/字符串最多打 200 个元素（默认 200，长了会截断）
set pagination off            # 不要一屏一屏地 --Type <RET>--
set confirm off               # 不要每次都问 y/n
set history save on           # 保存命令历史
set logging file gdb.log      # 把输出存下来
set logging on

3.5 脚本化 / 批处理（自动化生产分析）

# 一条命令导出 core 的全部线程栈，适合放进事故自动分析脚本
gdb -batch -ex "thread apply all bt full" -ex quit ./prog core > crash.txt

# 从脚本文件执行
gdb -x commands.gdb ./prog

3.6 处理 fork / exec

set follow-fork-mode child     # fork 后跟【子】进程（默认跟父进程）
set detach-on-fork off         # 父子都不放，可以来回切
set follow-exec-mode new

3.7 优化代码调试：<optimized out> 怎么办

症状处理
变量显示 <optimized out>改用 -Og（专为调试优化的等级）重编，或从寄存器 info registers 推
单步乱跳行号指令重排导致，用 -Og 或 -O0
栈缺失中间帧函数被内联；加 -fno-inline -fno-omit-frame-pointer
完全没有符号被 strip 了；用配套的 .debug 文件：symbol-file prog.debug

3.8 反向调试（知道就好）

record                # 开始记录
reverse-step / rs     # ★ 往【回】走一步
reverse-continue      # 回到上一个断点

能「时光倒流」，但极慢且限制多。实际生产更推荐 Mozilla 的 rr（rr record ./prog + rr replay），可确定性重放，是查偶现 bug 的利器。

4. 五个实战剧本

剧本 A · 段错误（SIGSEGV）

1. gdb ./prog core 2. bt ← 崩在哪一行 3. frame N ← 切到你自己的代码那一帧（不是库里那帧） 4. info locals / p ptr ← 看指针值 p ptr == 0x0 → 空指针 p ptr 是很小的数 → 空指针访问成员（0x8 = 第二个字段偏移） p ptr 是乱七八糟的值 → 野指针 / 已释放 / 栈被写坏 5. 如果栈本身是乱码 → 栈被破坏，换 ASan 重跑

剧本 B · 进程卡死 / 死锁

# 最快：不进 gdb，一条命令看全部线程栈
pstack <pid>          # 或 gstack / eu-stack

# 或者
gdb -p <pid> -batch -ex "thread apply all bt" -ex detach

剧本 C · 「谁改了我的变量」

gdb ./prog
start
watch g_config.timeout       # 或 watch -l obj->field
continue
# 一旦有人写它，gdb 立刻停下并打印：
#   Old value = 3000
#   New value = 0
bt                            # ← 凶手的调用栈就在这

剧本 D · 内存越界 / use-after-free

gdb 在这类问题上很吃力（崩溃点往往离案发现场很远），直接上 ASan：

g++ -g -O1 -fsanitize=address -fno-omit-frame-pointer main.cpp
./a.out
# ASan 会直接打印：
#   heap-buffer-overflow ... WRITE of size 4 at 0x...
#   #0 in appendOrder() order.cpp:88        ← 出事的地方
#   allocated by thread T0 here: ...        ← 这块内存是哪儿分配的
#   freed by thread T0 here: ...            ← 又是在哪儿释放的

剧本 E · 只在生产偶现

1. 确保 core 能落地：ulimit -c unlimited + core_pattern 配好 2. Release 也带 -g，不要 strip（把符号单独存一份归档） 3. 崩溃后自动跑批处理导出： gdb -batch -ex "thread apply all bt full" -ex quit ./prog core > crash.txt 4. 光靠 core 不够时： - 加轻量埋点（不改代码可用 gdb 的 commands，或 SystemTap / eBPF） - 灰度一台机器开 ASan / TSan 跑 - 用 rr 录制可复现的执行序列

5. Sanitizer · 现代首选

形象比喻

Sanitizer 是编译期给你的代码埋满摄像头：每次读写内存、每次加解锁都被记录。一旦有人越界或竞争，当场抓现行 —— 而不是等半小时后在别处崩掉。代价是程序变慢、变胖。

工具编译选项抓什么开销
ASan-fsanitize=address堆/栈/全局越界、use-after-free、double free、内存泄漏慢 2x，内存 3x
TSan-fsanitize=thread数据竞争、锁顺序反转慢 5~15x，内存 5~10x
UBSan-fsanitize=undefined有符号溢出、除零、空指针解引用、未对齐访问、错误的类型转换慢 1.2x
LSanASan 自带内存泄漏（也可单用 -fsanitize=leak）低
 
# 推荐的调试构建
g++ -g -O1 -fno-omit-frame-pointer -fsanitize=address,undefined main.cpp

# 运行期开关（环境变量）
ASAN_OPTIONS=detect_leaks=1:halt_on_error=0:log_path=./asan ./a.out
UBSAN_OPTIONS=print_stacktrace=1 ./a.out
TSAN_OPTIONS=second_deadlock_stack=1 ./a.out
三个必知
  • ASan 和 TSan 不能同时开（内存模型冲突），要分两次跑
  • 用 -O1 而不是 -O0：-O0 太慢，且某些检查依赖优化后的布局
  • TSan 只能发现「实际执行到的」竞争，所以要配合压力测试和多次运行，不是跑一遍没报就等于没问题

Sanitizer vs valgrind 怎么选

Sanitizervalgrind
是否需要重新编译需要不需要 ← 最大优势
速度慢 2~15x慢 10~50x
栈上越界✓ 能查✗ 查不到
未初始化变量需 MSan（较难用）✓ memcheck 强项
适用开发/CI 阶段常开拿到一个现成二进制就想查

结论：日常开发和 CI 用 Sanitizer；只有二进制、不能重编时用 valgrind。

6. valgrind 家族

valgrind 的原理是把程序放进一个虚拟 CPU 里跑，每条指令都被翻译和检查 —— 所以不用重编译，但很慢。

子工具用途
memcheck（默认）内存泄漏、非法读写、未初始化变量
helgrind / drd数据竞争、锁顺序错误
callgrind指令级 profiling，配 kcachegrind 看调用图
massif堆内存快照，画出「内存随时间增长曲线」+ 各处占比
 
# 查泄漏（最常用的一条）
valgrind --leak-check=full --show-leak-kinds=all \
         --track-origins=yes --log-file=vg.log ./prog

# 查内存增长是谁占的
valgrind --tool=massif ./prog
ms_print massif.out.1234

# 查数据竞争
valgrind --tool=helgrind ./prog

memcheck 报告怎么读

分类含义要紧吗
definitely lost确定泄漏，没有任何指针指向它必须修
indirectly lost因为它的父节点泄漏而连带泄漏修父节点即可
possibly lost只有指向内部的指针（常见于自定义分配器）看情况
still reachable程序结束时还有指针指着（全局单例、内存池）通常可以忽略

--track-origins=yes 能告诉你「这个未初始化的值是从哪来的」，值得多花那点时间。

7. perf 与火焰图

形象比喻

perf 是给正在跑的程序连续拍快照（默认每秒几百上千次），统计「每次拍到的时候你在执行哪一行」。拍到次数最多的地方，就是最耗时的地方。因为是采样而不是插桩，开销极低（几个百分点），可以直接在生产上用。

7.1 从粗到细的三步

# ① 先看整体健康度（不改代码，几秒出结果）
perf stat ./prog
#   关注：IPC、cache-misses、branch-misses、context-switches

# ② 实时看热点函数（像 top，但看的是函数）
perf top -p <pid>

# ③ 抓一段时间做详细分析
perf record -F 99 -g -p <pid> -- sleep 30
perf report            # 交互式浏览，回车展开调用链

7.2 perf stat 关键指标怎么读

指标健康值异常说明什么
IPC（每周期指令数）> 1.5 较好< 1 说明大量时间在等内存，是数据布局/cache 问题
cache-misses / cache-references< 5%高 → 数据不连续、伪共享、结构体太大
branch-misses< 2%高 → 分支不可预测，考虑无分支写法或排序输入
context-switches越低越好高 → 锁竞争激烈、线程过多
page-faults启动后应趋近 0持续增长 → 内存一直在新分配，或缺页没预热

7.3 火焰图

git clone https://github.com/brendangregg/FlameGraph

perf record -F 99 -g -p <pid> -- sleep 30
perf script > out.perf
./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
./FlameGraph/flamegraph.pl out.folded > flame.svg
前提

必须编译时加 -fno-omit-frame-pointer，否则 -g 抓到的调用栈是断的。或者用 perf record --call-graph dwarf（更准但开销大）。

8. strace / ltrace · 看它到底在干什么

形象比喻

strace 是在程序和操作系统之间装了个窃听器：所有系统调用（开文件、读写、网络、锁等待）连同参数和返回值都被记下来。程序可以骗你，系统调用不会。

strace -f -T -tt -p <pid>        # 跟踪运行中的进程
#   -f  跟踪子进程/线程
#   -T  ★ 显示每个调用【耗时】—— 找卡顿神器
#   -tt 显示时间戳

strace -c ./prog                  # ★ 汇总统计：哪个 syscall 调用最多/最慢
strace -e trace=openat ./prog     # 只看开文件（找配置文件在哪）
strace -e trace=network ./prog    # 只看网络
strace -o out.txt -f ./prog       # 输出到文件

ltrace ./prog                     # 看【库函数】调用（malloc/strcpy 等）

典型判读

看到什么说明
卡在 futex(...) 很久在等锁（pthread mutex/条件变量底层就是 futex）
卡在 epoll_wait / poll正常空闲，在等事件
卡在 read / write 且耗时长IO 慢，或对端不回
大量 openat(...) = -1 ENOENT在到处找文件（库路径/配置路径不对）
大量 brk / mmap频繁申请内存 → 考虑内存池
密集的小 write没做缓冲，每条日志一次系统调用
EACCES / EPERM权限问题，一眼定位
注意

strace 会让程序慢几十倍（每个系统调用都要陷入 ptrace），生产上只能短时间使用，且对延迟敏感的服务要谨慎。更轻量的替代是 eBPF 系工具（bpftrace、bcc）。

9. 生产环境轻量工具箱

9.1 一键看线程栈

pstack <pid>        # 打印所有线程的调用栈，不用进 gdb
gstack <pid>        # 同上（有些发行版叫这个）
eu-stack -p <pid>   # elfutils 版本，更快

9.2 /proc/<pid>/ 是个宝库

路径能看到什么
statusVmRSS（真实物理内存）、VmSize、线程数、上下文切换次数
maps / smaps内存段布局、加载了哪些 so 及其地址、每段实际占用
fd/打开了哪些文件和 socket（ls -l 看得到）
limits该进程实际生效的 ulimit（排查「为什么没生成 core」）
task/<tid>/stack内核态栈
environ启动时的环境变量（排查配置不生效）

9.3 系统级观测

top -H -p <pid>      # -H 按【线程】显示，看是哪个线程吃 CPU
pidstat -t -p <pid> 1
vmstat 1              # r/b 队列、si/so 换页、cs 上下文切换
iostat -x 1           # %util、await —— 磁盘是不是瓶颈
free -h               # 注意看 available，不是 free
pmap -x <pid>         # 内存段明细
lsof -p <pid>         # 打开的文件/连接
ss -tanp              # 连接状态（替代 netstat，快得多）
tcpdump -i any port 8888 -w cap.pcap

9.4 二进制与符号

ldd ./prog                          # 依赖哪些动态库、实际解析到哪个路径
nm -C ./prog | grep Order            # 符号表（-C 自动 demangle）
c++filt _ZN5Order6submitEv           # 手动把 mangled 名字还原
addr2line -e ./prog -f -C 0x4005d6   # ★ 崩溃地址 → 文件:行号
objdump -d --source ./prog           # 反汇编并穿插源码
readelf -h ./prog                    # ELF 头
strings ./prog | grep version        # 看看编进去的版本号

addr2line 在「只有一行崩溃地址、没有 core」时特别救命（前提是拿到同一份带符号的二进制）。

10. 编译期就该开好的选项

构建类型推荐选项
日常开发-Og -g -Wall -Wextra -fsanitize=address,undefined -fno-omit-frame-pointer
CI 额外跑一遍-fsanitize=thread（单独一次，不能和 ASan 混）
Release-O2 -g -DNDEBUG -fno-omit-frame-pointer ← 保留 -g，不要 strip
STL 边界检查（调试构建）-D_GLIBCXX_ASSERTIONS（轻量）或 -D_GLIBCXX_DEBUG（严格但 ABI 不兼容）
安全加固-fstack-protector-strong -D_FORTIFY_SOURCE=2
两条最重要的

① Release 也要带 -g。调试符号不影响运行速度，只是二进制变大。可以用 objcopy --only-keep-debug 把符号单独抽出来归档，线上放精简版，出事时再配对分析。
② 加 -fno-omit-frame-pointer。只损失约 1% 性能，却是 perf 火焰图和完整调用栈的前提。

面试常被问的三句

「你怎么排查线上问题？」先按现象分类：崩溃看 core、卡住看线程栈、慢看 perf、行为怪看 strace；能复现就上 Sanitizer。
「gdb 你用得最多的功能是什么？」thread apply all bt 查死锁、条件断点定位特定数据、watch 找谁改了变量。
「ASan 和 valgrind 区别？」ASan 要重编译但快、能查栈越界，适合开发和 CI；valgrind 不用重编译、能查未初始化变量，适合只有二进制的场景。

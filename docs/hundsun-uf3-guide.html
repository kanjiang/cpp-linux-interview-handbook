前言

恒生经纪业务核心载体为 UF3.0 新一代全内存交易柜台。岗位核心诉求：基于 C++ 开发低延迟交易内核、订单链路处理、内存状态管理、WAL 日志持久化、进程故障恢复、风控模块开发。

技术考察偏向 高性能 C++ + Linux 底层 + 交易架构 + 金融业务融合，区别于互联网后端：低延迟、无 GC 停顿、订单零丢失、状态强一致。

第一篇 · 金融场景高性能 C++ 核心知识点

1.1 面向对象与类设计

1.1.1 虚函数与多态

  • 带虚函数的类有虚表，对象头部通常有 vptr。
  • 基类析构必须 virtual，否则派生对象经基类指针删除会泄漏（持仓/订单对象尤其危险）。
  • 重载：同名不同参数，编译期绑定；重写：派生类覆盖 virtual，运行期绑定；隐藏：派生类同名函数屏蔽基类同名重载集。
  • 交易代码强制 override；固定业务结构体可用 final 禁止继承。

1.1.2 五大法则（交易对象必考）

  • 五法则：拷贝构造、拷贝赋值、移动构造、移动赋值、析构。
  • Order / Hold 等热对象常 禁用拷贝：= delete，只保留移动，避免拷贝带来延迟抖动。
  • 移动函数加 noexcept，便于容器优化。
  • 连接/文件/内存块用 RAII，避免长驻进程句柄泄漏。

1.1.3 const 系列

  • const 变量：费率、基础配置等冻结常量。
  • const 成员函数：余额/持仓查询只读接口，防止查询路径改状态。
  • const int* 内容不可改；int* const 指针地址不可改。
  • constexpr：编译期常量，减少运行期取值开销。

1.2 内存管理（全内存柜台重中之重）

1.2.1 malloc/new 与内存池

  • malloc 只分配；new 分配并构造。
  • 热路径频繁 malloc/free 易碎片与抖动。
  • 柜台方案：启动预分配内存池，划分 Order/Fund/Hold 固定节点；下单取节点、完结归还；可用 placement new：new (ptr) Order()。

1.2.2 智能指针选型

类型 原理 柜台场景 慎用/禁用
unique_ptr 独占，无原子计数 订单、会话句柄首选 真共享生命周期时不够用
shared_ptr 引用计数有原子开销 低频共享状态 下单热路径慎用
weak_ptr 破环、观察 缓存关联观察 核心撮合链路不依赖它做所有权

结论：热路径优先 unique_ptr，避免 shared_ptr 原子操作带来延迟波动。

1.2.3 STL 与交易适配

  • vector：缓存友好，委托/撮合队列常用；必须 reserve 防扩容拷贝。
  • unordered_map：冲突退化风险；账户映射可考虑自定义开放寻址。
  • map：有序遍历委托编号等。
  • 禁止边遍历边删导致迭代器失效。

1.2.4 高性能拔高点

  • 移动语义 + RVO/NRVO，减少返回对象拷贝。
  • 缓存行对齐（常 64B），规避伪共享；多线程独立账户状态隔离到不同缓存行。
  • 热路径禁用异常：用错误码，避免不可控跳转延迟。

1.3 C++11 并发

1.3.1 锁选型

  • mutex：临界区含日志 IO/落盘等长耗时。
  • 自旋锁：短临界区改资金/持仓，柜台内存状态修改常首选。
  • shared_mutex：高频读、低频写（查余额 vs 冻结资金）。

1.3.2 atomic 与内存序

  • 适用：委托计数、成交笔数、序列号等。
  • relaxed：只要原子性，统计可用。
  • acquire/release：常见可见性配对，无锁基础。
  • seq_cst：最严最贵，仅关键标记慎用。

1.3.3 配套组件

  • condition_variable：线程池等待；用 while 防虚假唤醒。
  • thread_local：线程私有日志缓冲/临时对象，减少全局争用。
  • 死锁四条件：互斥、占有且等待、不可抢占、环路等待；统一锁顺序规避。

第二篇 · Linux 系统与网络

2.1 内核与稳定性

  • UF3.0 常见：多线程单进程；撮合核心单线程串行，网络 IO 多线程接入。
  • mmap：WAL 映射减少 write；共享内存投递网关→内核，延迟常低于 socket。
  • sendfile 等零拷贝：回报发送少一次拷贝。
  • OOM：调 oom_score_adj、拆分进程，避免单进程过大。
  • SIGSEGV/SIGABRT + core；systemd 托管自动拉起；SIGCHLD 回收防僵尸进程。

排查工具

  • gdb：core / 附着排死锁死循环
  • perf：CPU 热点
  • strace：系统调用阻塞（fsync/socket）
  • vmstat/free：内存池是否顶满

2.2 网络 IO

  • epoll 替代 select/poll，适配海量连接。
  • LT：有数据就通知；ET：状态变化通知一次，触发后循环读到 EAGAIN。
  • 多 Reactor：主线程 accept，子线程 IO，业务线程池解析订单（网关常见）。
  • TCP_NODELAY：关 Nagle，下单包立即发。
  • 粘包：长度头 + 业务体；SO_REUSEADDR 快速重启绑定；注意 TIME_WAIT 与端口复用。

第三篇 · UF3.0 全内存交易架构（最高频）

3.1 核心思想

内存做交易，磁盘做兜底。账户/资金/持仓/委托/成交等热数据常驻内存；热路径规避磁盘随机 IO；磁盘用 WAL + 快照做持久化、恢复、审计。

  • 收益：微秒级访问，支撑高 TPS。
  • 代价：一致性、恢复、容量、对账复杂度更高。

四层拆解（必背）

  1. 内存数据结构建模
  2. 状态机与并发控制
  3. 持久化：WAL + Snapshot
  4. 故障恢复 + 三方对账

3.2 订单全链路五步（必背）

  1. 接入校验：网关解析、前置风控，合规单进核心进程。
  2. 内存处理：查资金/持仓，冻结，建委托，可撮合则内存撮合，无磁盘随机读写。
  3. 持久化：先改内存，再同步/异步写 WAL；强一致用 fsync，极致延迟可异步。
  4. 崩溃恢复：加载最近快照 + 重放之后 WAL，重建内存态。
  5. 对账闭环：内存态、WAL、交易所回报交叉核对。

3.3 WAL 与 Snapshot

  • WAL 准则：状态变更先落日志，再对外成功应答，防丢单。
  • 刷盘：高风险业务同步 fsync；普通业务可异步，靠对账兜底。
  • Snapshot：低峰全量固化，缩短恢复时重放窗口。

3.4 经典三问

为什么快？

  • 热数据在内存，避开 DB 随机 IO。
  • 预分配内存池，热路径少 malloc。
  • 撮合单线程减锁竞争；TCP_NODELAY 降网络时延。

一致性从哪来？

  • WAL 留痕 + 快照基线。
  • 内存 / 日志 / 交易所回报三方对账。
  • 委托状态机约束冻结解冻时序。

宕机丢单吗？

  • 成功应答前确保 WAL 已落盘（按业务等级）。
  • 恢复：快照 + 重放 WAL。
  • 已报交易所的单，恢复后主动查交易所终态补齐。

3.5 风险点（加分）

  • 内存容量：冷热分离，休眠账户落库。
  • 日志损坏：多副本/RAID。
  • 并发错乱：同账户短临界区自旋/串行队列。
  • OOM：调优先级、拆进程。

第四篇 · 证券经纪业务基础

4.1 端到端链路

客户端 → 前置网关 → UF3.0 全内存柜台 → 报盘机 → 交易所 → 成交回报回柜台 → 更新内存资金持仓 → 客户端展示 → 日终中证登清算过户。

4.2 委托状态机

  • 已报：校验通过并冻结，已上报。
  • 部成 / 已成：部分或全部成交。
  • 已撤：撤销未成交，返还冻结。
  • 废单：校验失败，即时释放冻结。

难点：已上报后柜台宕机，恢复后需主动查交易所状态补全。

4.3 资金与持仓

  • 买：下单冻资金，成交扣资金加持仓。
  • 卖：下单冻股份，成交减股份加资金。
  • A 股 T+1：区分可卖持仓与当日持仓。

4.4 盘中 vs 日终

  • 盘中：内存实时委托与冻结解冻；DB 多用于查询归档。
  • 日终：批量落库，对接中国结算过户，修正盘中临时记账差异。

4.5 风控常见项

权限、涨跌停、单笔上限、限售拦截、反高频、日内次数限制等。

第五篇 · 高频真题话术

技术题

为何用 C++ 而非 Java/Go？

避免 GC STW；可精细内存池与缓存行优化；无重型运行时；时延更确定。

自旋锁 vs 互斥锁？

短临界区无 IO → 自旋；含 fsync/DB/网络 → 互斥，避免空转。

伪共享？

多线程写同一缓存行不同字段导致缓存行来回失效；结构体按缓存行对齐隔离。

业务架构题

一笔限价买单完整流程？

  1. 网关校验账户与交易时间
  2. 内核读可用资金，校验金额与涨跌停
  3. 冻结资金，建委托入队
  4. 写 WAL（按策略刷盘）后回已报
  5. 撮合成交：扣冻结、加持仓，推送/对回报
  6. 异常靠快照+WAL 恢复；日终归档

异步刷盘断电丢单？

高风险同步 fsync；普通异步 + 交易所回报对账补齐；日志多副本防盘坏。

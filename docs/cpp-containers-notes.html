0. 总览：它们是同一类东西 —— 资源管家

这四个的共同身份是：帮你管资源，让你不用写 new / delete。

它管的是什么 比喻 std::vector<T> → 一片可变长的对象数组 会自动扩建的储物柜 std::string → 一串字符 专门装字的储物柜（自带小口袋） std::unique_ptr → 一个对象，独占 只有一把的钥匙 std::shared_ptr → 一个对象，共享 合租房 + 门口的人数计数牌

它们都遵守 RAII：构造时拿资源，析构时自动还 —— 无论你是正常返回、提前 return、还是抛异常。

1. std::vector · 会自动扩建的储物柜

形象比喻

你租了一排连号的储物柜（连续内存）。柜子编号连续，所以按编号取东西极快（v[i] 就是地址加偏移）。柜子租满了怎么办？去租一排更大的（通常是 2 倍），把东西全搬过去，退掉旧的。

1.1 内存布局：其实就三个指针

所以 sizeof(std::vector<int>) 是固定的（一般 24 字节），跟里面装多少东西无关 —— 数据全在堆上。

1.2 size vs capacity（必分清）

含义比喻
size()实际装了几个用了几个柜子
capacity()最多能装几个而不用搬家一共租了几个柜子
 
std::vector<int> v;
v.reserve(1000);      // 先租 1000 个柜子，但一个没用
// size() == 0, capacity() == 1000

for (int i = 0; i < 1000; ++i)
    v.push_back(i);   // ✓ 全程零次扩容、零次搬家

reserve 是最容易拿到的性能优化：知道大概多少个就先 reserve。

函数改 size改 capacity说明
reserve(n)否扩到 ≥n只订柜子，不放东西
resize(n)是可能扩真的构造/销毁元素
shrink_to_fit()否缩到 size退掉多余的柜子（非强制）
clear()变 0不变东西清空，柜子还租着

clear() 不释放内存 —— 想真正还回去用 std::vector<T>().swap(v)，或 clear() + shrink_to_fit()。

1.3 扩容为什么是「2 倍」而不是「加 1」

每次 +1： 加 n 个元素要搬 1+2+3+...+n = O(n²) 次 每次 ×2： 搬家次数 1+2+4+8+...+n ≈ 2n = O(n) 次 摊到每个元素上 → 【摊还 O(1)】

这就是「摊还常数时间」的由来。libstdc++ 用 2 倍，MSVC 用 1.5 倍。

1.4 迭代器失效 —— vector 最大的坑

易踩坑

扩容会让所有指针、引用、迭代器全部失效（东西搬到新柜子了，旧地址成了野指针）。

std::vector<int> v{1,2,3};
int& r = v[0];          // 拿了个引用
v.push_back(4);         // ← 可能扩容
std::cout << r;         // ✗ 悬空引用，未定义行为
// ✗ 错误：erase 后 it 失效了
for (auto it = v.begin(); it != v.end(); ++it)
    if (*it < 0) v.erase(it);

// ✓ 正确：erase 返回下一个有效迭代器
for (auto it = v.begin(); it != v.end(); )
    it = (*it < 0) ? v.erase(it) : it + 1;

// ✓ 更好：erase-remove 惯用法
v.erase(std::remove_if(v.begin(), v.end(),
                       [](int x){ return x < 0; }),
        v.end());
// C++20：std::erase_if(v, [](int x){ return x < 0; });
操作失效范围
push_back / insert 且扩容全部
push_back 未扩容只有 end()
insert 未扩容插入点之后的全部
erase删除点之后的全部

1.5 为什么快：cache 友好

vector： [A][B][C][D][E] ← 内存连续，一次 cache line 拉进来一串 list： [A]→ ... [C]→ ... [B] ← 内存散落，每跳一次就 cache miss

现代 CPU 上，遍历 vector 常常比 list 快 10 倍以上，即使理论复杂度一样。所以：默认就用 vector，除非有明确理由不用。

1.6 vector<bool> 是个假容器

易踩坑

它被特化成了位图（1 个 bool 占 1 bit），operator[] 返回的是代理对象而不是 bool&。

std::vector<bool> v(10);
bool& r = v[0];         // ✗ 编译错误
auto x = v[0];          // ✗ x 的类型是代理，不是 bool
bool* p = &v[0];        // ✗ 取不到地址

替代方案：用 std::vector<char> 或 std::deque<bool>。

2. std::string · 自带小口袋的储物柜

本质上 std::string ≈ std::vector<char> + 一堆文本操作 + SSO + 末尾隐含的 '\0'。size()、capacity()、reserve()、扩容规则、迭代器失效 —— 和 vector 完全一样。

2.1 核心优化：SSO（小字符串优化）

形象比喻

现实中的字符串绝大多数很短（"id"、"OK"、"600519"）。为这么短的东西跑一趟 new 太亏了，所以 string 在自己身上缝了一个小口袋 —— 短字符串直接塞口袋里（栈上），根本不碰堆。

实现（64 位）sizeof(string)SSO 能存几个字符
libstdc++ (GCC)3215
libc++ (Clang)2422
MSVC3215

实践含义：短字符串的拷贝几乎免费；一旦超过 15/22 字符，每次拷贝就是一次堆分配。热路径上要留意。

SSO 带来的两个反直觉后果

一、短字符串 std::move 并不省事。移动一个长串是偷指针，O(1) 且不碰内容；但短串的内容就住在对象自己身上，没有指针可偷，只能照样把那 15/22 个字节拷过去。「移动一定比拷贝快」这句话在 SSO 串上不成立。
二、data() / c_str() 的指针会随对象一起搬家。处于 SSO 状态时这个指针指向对象内部，所以对象一旦被移动、被 vector 扩容搬走、或者按值返回，之前存下来的旧指针立刻悬空。长串反而没这个问题——它指向堆，对象搬家不影响堆地址。这也是 std::string 不能被简单按位搬迁的原因。

2.2 常用操作

std::string s = "hello";

s += " world";                 // 追加
s.append(3, '!');              // "hello world!!!"
s.substr(0, 5);                // "hello"（返回【新对象】，有拷贝）
s.find("wor");                 // 返回下标，找不到返回 std::string::npos
s.replace(0, 5, "HELLO");
s.c_str();                     // 拿到 const char*，保证以 '\0' 结尾（给 C API 用）
s.data();                      // C++17 起等同 c_str()
两个高频坑

① find 找不到时返回 npos（一个很大的 size_t），不是 -1：

if (s.find("x") != std::string::npos) { ... }   // ✓ 必须这样判断
if (s.find("x") >= 0) { ... }                   // ✗ 永远为真

② c_str() 的悬空陷阱：

const char* p = getName().c_str();    // ✗ 临时 string 立刻析构，p 悬空
use(p);

std::string s = getName();             // ✓ 先接住
use(s.c_str());

2.3 std::string_view（C++17）· 只看不拿

形象比喻

string 是一本书，string_view 是一张写着「第几页到第几页」的便条 —— 只是「指针 + 长度」的轻量视图，不拥有数据、不分配内存。

void log(const std::string& s);
log("hello");            // ✗ 从字面量构造了一个临时 string → 可能有堆分配

void log(std::string_view s);    // ✓ 零拷贝
log("hello");                    // 直接指向字面量
log(myString);                   // 直接指向 myString 的缓冲区
易踩坑

它不延长生命周期 —— 原字符串没了，view 就悬空。

std::string_view sv;
{
    std::string s = "temp";
    sv = s;
}                    // s 销毁
use(sv);             // ✗ 悬空

用法规则：适合做函数参数（只读、不保存）；不要存成成员变量，除非能确保底层数据活得更久。

3. std::unique_ptr · 只有一把的钥匙

形象比喻

你手上有一栋房子的唯一钥匙：全世界只有这一把，不能复印（禁止拷贝）；可以交给别人（std::move），交出去后你手上就没了；你走的时候（离开作用域），自动把房子拆了（delete）。

{
    auto p = std::make_unique<Order>(123);
    p->submit();
}   // ← p 析构，Order 自动 delete，不管中间是 return 还是抛异常

3.1 关键特性：零开销

sizeof(std::unique_ptr<int>) == sizeof(int*)    // 通常 8 字节，一模一样
结论

它就是个裸指针的壳，运行期没有任何额外代价，所有安全性都在编译期完成。所以不要因为「怕慢」而用裸指针 new/delete。

3.2 常用操作

auto p = std::make_unique<Order>(id, price);   // ✓ 永远优先 make_unique（C++14）

auto q = p;              // ✗ 编译错误：不能拷贝
auto q = std::move(p);   // ✓ p 变成 nullptr

p->submit();             // 像指针一样用
*p;                      // 解引用
p.get();                 // 拿裸指针（传给 C API，但【不要】让别人 delete 它）
p.reset();               // 立刻释放，p 变 nullptr
p.reset(new Order(...)); // 释放旧的，接管新的
auto raw = p.release();  // 【放弃所有权】，返回裸指针，从此你要自己 delete
if (p) { ... }           // 判空

3.3 数组版本与自定义删除器

auto arr = std::make_unique<int[]>(100);   // 用 delete[] 释放，支持 operator[]

// 包装 C 资源：无论怎么退出，fclose 一定被调用
auto closer = [](FILE* f) { if (f) fclose(f); };
std::unique_ptr<FILE, decltype(closer)> fp(fopen("a.txt", "r"), closer);
注意

带状态的删除器（函数指针、有捕获的 lambda）会让 unique_ptr 变大：

std::unique_ptr<FILE, decltype(&fclose)> fp(...);   // sizeof = 16（多存了函数指针）
std::unique_ptr<FILE, FdCloser> fp2(...);           // sizeof = 8（空类，被 EBO 优化掉）

优先用无状态的函数对象 / 无捕获 lambda。

3.4 典型应用：工厂函数 + 多态

std::unique_ptr<Strategy> createStrategy(Type t) {
    switch (t) {
        case Type::TWAP: return std::make_unique<TwapStrategy>();
        case Type::VWAP: return std::make_unique<VwapStrategy>();
    }
}

auto s = createStrategy(Type::TWAP);   // 所有权明确地交给调用方

⚠️ 通过基类指针删除时，基类必须有虚析构函数（virtual ~Strategy() = default;），否则派生类部分不会被析构。

4. std::shared_ptr · 合租房与门口的计数牌

形象比喻

一栋房子，很多人都有钥匙。门口挂着一块计数牌：每多一个人拿钥匙 → 计数 +1；每有一个人走掉 → 计数 −1；最后一个走的人关灯拆房（计数归 0 → delete 对象）。

auto p1 = std::make_shared<Order>(123);   // 计数 = 1
{
    auto p2 = p1;                         // 计数 = 2
    auto p3 = p1;                         // 计数 = 3
}                                          // p2 p3 析构 → 计数 = 1
                                           // p1 析构 → 计数 = 0 → Order 被 delete

4.1 内存布局：两个指针 + 堆上的控制块

sizeof(std::shared_ptr<int>) == 16 // 是 unique_ptr 的两倍 shared_ptr 对象： ┌───────────┬────────────────┐ │ 对象指针 │ 控制块指针 │ └─────┬─────┴────────┬───────┘ ↓ ↓ [ Order 对象 ] ┌─────────────────┐ │ 强引用计数(原子) │ │ 弱引用计数(原子) │ │ 删除器 │ │ 分配器 │ └─────────────────┘

4.2 make_shared vs new：一次分配 vs 两次

std::shared_ptr<Order> p(new Order(1));      // ✗ 两次堆分配：对象 + 控制块
auto p = std::make_shared<Order>(1);         // ✓ 一次分配，对象和控制块【挨在一起】
new 版本： [Order] ... 远处 ... [控制块] ← 两次 malloc，两处 cache miss make 版本： [控制块|Order] ← 一次 malloc，cache 友好

make_shared 还能避免异常时的内存泄漏：f(std::shared_ptr<A>(new A), g()) 中若求值顺序是 new A → g() 抛异常 → 那个 A 就泄漏了。

make_shared 的唯一缺点

因为对象和控制块在同一块内存，只要还有 weak_ptr 活着，那块内存就不能释放（对象已析构，但内存还占着）。对象很大 + weak_ptr 长寿时，用 new 版本反而好。

4.3 坑一：从同一个裸指针构造两次

易踩坑 
Order* raw = new Order(1);
std::shared_ptr<Order> p1(raw);
std::shared_ptr<Order> p2(raw);   // ✗ 【两个独立的控制块】，各自计数为 1
                                  // → 析构时 double free，程序崩溃
错误状态： p1 → [控制块A: 1] ┐ ├→ [同一个 Order] ← 会被 delete 两次 p2 → [控制块B: 1] ┘

铁律：一个裸指针只能交给 shared_ptr 一次。最好的办法是根本不出现裸指针 —— 永远用 make_shared，复制时从已有的 shared_ptr 复制。

4.4 坑二：在成员函数里 shared_ptr<T>(this)

class Session {
    void start() {
        registerCallback(std::shared_ptr<Session>(this));   // ✗ 新建控制块 → double free
    }
};

正解是继承 std::enable_shared_from_this：

class Session : public std::enable_shared_from_this<Session> {
public:
    void start() {
        registerCallback(shared_from_this());   // ✓ 复用已有的控制块
    }
};

auto s = std::make_shared<Session>();   // ★ 前提：对象本身必须由 shared_ptr 管理
s->start();

⚠️ 不能在构造函数里调用 shared_from_this()（那时控制块还没建好）。

4.5 坑三：循环引用 → 永久泄漏

struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;    // ✗ 互相持有
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;
// 离开作用域后：外部引用没了，但它们【互相】还各持有对方一个引用
// → 计数都停在 1 → 永远不会被释放

解法：把其中一个方向改成 weak_ptr（观察但不持有）：

struct Node {
    std::shared_ptr<Node> next;   // 强：我负责下一个的生命周期
    std::weak_ptr<Node>   prev;   // 弱：我只是能看到上一个，不管它死活
};
通用规则

父持子用 shared_ptr，子回指父用 weak_ptr。观察者、缓存、回调也一律用 weak_ptr。

std::weak_ptr<Node> w = sp;

if (auto sp2 = w.lock()) {    // ★ 必须先 lock 提升成 shared_ptr
    sp2->doSomething();        // 在这个作用域里对象保证活着
} else {
    // 对象已经被销毁了
}

w.expired();      // 检查是否已失效（但 check 完再 lock 有竞态，直接 lock 更好）
w.use_count();    // 强引用计数

4.6 坑四：线程安全的边界

内容线程安全？
引用计数的增减✓ 安全，是原子操作
多线程读同一个 shared_ptr（只拷贝，不改）✓ 安全
多线程同时读写同一个 shared_ptr 变量✗ 不安全，需加锁或用 std::atomic<std::shared_ptr>（C++20）
多线程访问它指向的对象✗ 不安全，对象本身该加锁还得加锁
一句话记忆

shared_ptr 保证「计数」是线程安全的，不保证「指针本身」和「指向的对象」是线程安全的。

4.7 性能代价

unique_ptrshared_ptr
大小8 字节16 字节
堆分配1 次（对象）1~2 次（+控制块）
拷贝✗ 不可原子递增（多核竞争时开销明显）
析构直接 delete原子递减 + 判零

热路径上频繁拷贝 shared_ptr 是常见的性能问题 —— 传参时用 const shared_ptr<T>& 或直接传 T&，避免不必要的计数抖动。

5. 排序 · std::sort 的契约与选型

有了 std::sort，生产代码里基本不需要再手写排序算法了 —— 冒泡尤其可以说永远不需要。但「不用写」不等于「不用懂」：真正会出事的地方不是算法，而是调用契约。

5.1 std::sort 是三个算法拼出来的

典型实现是 introsort（内省排序）。那些手写算法并没有消失，只是搬进了标准库里 —— 唯独冒泡不在其中，因为它在任何数据分布下都没有优势。

5.2 比较器必须是严格弱序 —— 写成 <= 会读越界

这是 std::sort 最容易出事、也最容易被误判的一条契约：比较器必须表达严格弱序，也就是必须用 <，不能用 <=。写错的后果不是「顺序不对」，而是未定义行为。

// ✗ 未定义行为：相等时返回 true，违反严格弱序
std::sort(v.begin(), v.end(),
          [](const A& a, const A& b) { return a.key <= b.key; });

// ✓ 相等时必须返回 false
std::sort(v.begin(), v.end(),
          [](const A& a, const A& b) { return a.key < b.key; });

// 多字段排序：用 tuple 比较，天然满足严格弱序
std::sort(v.begin(), v.end(), [](const A& a, const A& b) {
    return std::tie(a.price, a.seq) < std::tie(b.price, b.seq);
});

// 降序不要写 >=，写 > 就够了（> 本身也是严格弱序）
std::sort(v.begin(), v.end(), std::greater<>{});
调试期就能抓住它

libstdc++ 加 -D_GLIBCXX_DEBUG、libc++ 加 -D_LIBCPP_ENABLE_ASSERTIONS=1，标准库会主动校验比较器是否构成严格弱序，把这类问题在测试阶段就报出来，而不是等到线上偶发段错误。

5.3 稳定性：sort 打乱相等元素，stable_sort 不打乱

std::sort 不稳定：key 相等的元素，相对顺序会被打乱。需要保序就用 std::stable_sort —— 有足够额外内存时是 O(n log n)，内存不够时退化成 O(n log² n)。

一个很常见的错法

「先按次要字段排、再按主要字段排」这个技巧只对 stable_sort 成立。用 std::sort 这么做，第二遍会把第一遍的结果打乱，结果是错的。要么全程用 stable_sort，要么写一个把所有字段都比完的复合比较器（就像上面 std::tie 那样）。

5.4 只需要更少的时候，别整体排序

这一条带来的收益通常比换排序算法大得多 —— 很多「排序太慢」其实是根本不需要排序：

需求该用什么复杂度
要全体有序std::sortO(n log n)
只要前 k 个，且这 k 个内部要有序std::partial_sortO(n log k)
只要第 k 个，或只要「前 k 个是哪些」而不管其内部顺序std::nth_element平均 O(n)
只要按条件分成两堆std::partitionO(n)
要保持相等元素的原有顺序std::stable_sortO(n log n)（内存够）
数据一直在变，随时要最大/最小std::priority_queue取顶 O(1)，增删 O(log n)
容器是 std::listlist::sort 成员函数O(n log n)

std::sort 要求随机访问迭代器，所以 std::list（双向迭代器）用不了它，得用自带的 list::sort 成员函数（内部是归并排序，不搬元素、只改指针）。

再往新一点：C++17 起可以写 std::sort(std::execution::par, v.begin(), v.end()) 一行开并行；C++20 起可以直接 std::ranges::sort(v)，省掉两个迭代器。

5.5 什么时候还真得自己写

确实存在 std::sort 覆盖不到的场景，但每一个都有明确理由，不是为了练手：

  • 键是整数、且值域已知 —— 基数排序 / 计数排序是 O(n) 的。比较排序的 O(n log n) 下界只对「只能两两比较」这个模型成立，一旦能直接拿键当下标就绕过去了。低延迟场景里按价格档位排委托（定点整数、档位有限）常常明显更快。
  • N 极小且固定（永远只排 4 个、8 个）—— 排序网络能编译成一串无分支的 min/max 指令，没有循环、没有分支预测失败。
  • 数据大于内存 —— 外部排序（分块排好落盘，再多路归并）。
  • GPU 或需要严格控制内存分配的场合。
面试怎么答

问「还需要手写排序吗」，先答生产代码不需要，冒泡永远不需要，再说清 std::sort 是 introsort、三段算法各补一块短板。然后主动把话题引到契约上：比较器必须严格弱序（< 不是 <=，写错是 UB 而不是结果错）、sort 不稳定、以及「只要第 k 个就用 nth_element」。最后补一句基数排序能突破 O(n log n) 下界的前提。能这样答，比手写一遍快排更能说明你在真实项目里排过序。

三条实践铁律

  1. 默认用 vector，除非有明确理由换别的容器。
  2. 默认用 unique_ptr，只有真的需要共享时才升级到 shared_ptr（unique_ptr 可随时 std::move 转成 shared_ptr，反过来不行）。
  3. 代码里不该出现裸 new / delete —— 一律 make_unique / make_shared。
一页背诵

vector＝会自动扩建的连号储物柜。三个指针 + 堆数组，满了就 ×2 搬家（摊还 O(1)），搬家后所有迭代器失效。reserve 是免费的性能，cache 友好，默认首选。
string ≈ vector<char> + SSO（短串直接存对象里，约 15/22 字符）。只读传参用 string_view，但它不延长生命周期。
unique_ptr＝唯一的一把钥匙，零开销（8 字节），只能移动不能拷贝，走时自动拆房。多态删除记得虚析构。
shared_ptr＝合租房 + 门口原子计数牌，最后一个走的人关灯。16 字节 + 控制块，优先 make_shared。三大坑：循环引用（配 weak_ptr 破）、同一裸指针建两次、线程安全只保证计数。

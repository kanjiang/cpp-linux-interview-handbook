1. epoll · 从挨个点名到谁有事自己举手

形象比喻

假设你是老师，班上一万个学生，要知道谁举手了。select 是每轮把全班名单交给教务处，教务处从头看到尾说「有人举手了」，你再自己从头找一遍是谁。epoll 是教务处那边常驻一份名单（不用每次交），门口挂个信箱，谁举手谁自己往信箱投条子，你只需要看信箱。

方式做法问题
阻塞 IO盯着一个学生等他举手一次只能管一个
select每次把整个 fd 集合拷进内核，返回后自己 O(n) 遍历找反复拷贝；两次 O(n)；最多 1024 个
poll同上，改用数组，无数量上限仍然每次拷贝 + O(n) 遍历
epollfd 常驻内核；就绪时由回调挂进就绪链表O(1)，只返回就绪的那几个

1.1 内核里的结构

关键区别：select/poll 是「主动轮询」，epoll 是「被动回调」。

1.2 三个函数

int epfd = epoll_create1(0);                  // 造一个 epoll 实例

struct epoll_event ev;
ev.events  = EPOLLIN;                          // 关心可读
ev.data.fd = sockfd;                           // 附带信息（也可放指针）
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev);  // 注册（ADD / MOD / DEL）

struct epoll_event events[1024];
int n = epoll_wait(epfd, events, 1024, -1);    // 等，返回就绪个数

for (int i = 0; i < n; ++i) {
    handle(events[i].data.fd);                 // 直接就是就绪的，无需遍历全部
}
事件含义
EPOLLIN / EPOLLOUT可读 / 可写
EPOLLERR / EPOLLHUP出错 / 挂断（总会被通知，不用注册）
EPOLLRDHUP对端关闭了写端 —— 检测断连的关键
EPOLLET边缘触发
EPOLLONESHOT触发一次后自动禁用，需重新 MOD 启用

1.3 LT vs ET（必考）

形象比喻

水平触发 LT（默认）：只要缓冲区里还有数据，我就一直提醒你 —— 像闹钟响个不停，直到你把事办完。
边缘触发 ET：只在「从没有到有」的那一瞬间提醒你一次 —— 像门铃只响一声，没听见就没了。

LTET
通知次数有数据就一直通知状态变化时通知一次
是否必须一次读完否，可以慢慢读必须读到 EAGAIN 为止
是否必须非阻塞否必须 O_NONBLOCK
系统调用次数多少
编程难度简单，不易错容易漏数据

ET 的正确写法（这个循环是标志性的）：

// 前提：fd 已设为 O_NONBLOCK
while (true) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n > 0) {
        process(buf, n);
    } else if (n == 0) {
        closeConn(fd);              // 对端正常关闭
        break;
    } else {
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;  // ✓ 读干净了
        if (errno == EINTR) continue;                        // 被信号打断，重试
        closeConn(fd);                                       // 真错误
        break;
    }
}
为什么 ET 必须非阻塞

你要循环读到 EAGAIN 才知道读完了；如果 fd 是阻塞的，最后那次没数据的 read 会永久卡死整个事件循环。

1.4 惊群与 Reactor

惊群问题：多个线程/进程都在 epoll_wait 同一个监听 fd，来一个连接把所有人都吵醒，但只有一个能 accept 成功。解法是 EPOLLEXCLUSIVE（Linux 4.5+，只唤醒一个）或 SO_REUSEPORT（每线程一个独立 listen fd，内核负载均衡，Nginx 的做法）。

主从 Reactor（muduo / Netty / Nginx 的架构）： 主 Reactor（1 个线程） 只负责 accept 新连接 │ └→ 轮流分发给 ──→ 从 Reactor 1（各自一个 epoll + 线程） ──→ 从 Reactor 2 ──→ 从 Reactor N 每个连接固定归属一个线程 → 该连接内无需加锁
面试一句话

select/poll 每次都要把全部 fd 拷进内核并 O(n) 遍历，epoll 用红黑树常驻注册 + 就绪回调链表，epoll_wait 只返回就绪的，复杂度与连接总数无关。ET 比 LT 少一半系统调用，但必须配非阻塞 fd 并循环读到 EAGAIN。

2. mmap · 给文件开一扇窗，不用来回搬箱子

2.1 传统 read 与 mmap 的路径差别

形象比喻

read 是「派人去仓库把货搬到你办公室」；mmap 是「在你办公室墙上开一扇窗，直接看仓库」—— 货一直在仓库，你看的就是原件。

2.2 最小可用写法

int fd = open("data.bin", O_RDONLY);
struct stat st; fstat(fd, &st);

char* p = (char*)mmap(nullptr, st.st_size, PROT_READ, MAP_SHARED, fd, 0);

// 现在像操作数组一样操作文件，没有 read、没有拷贝
std::cout << p[12345];

munmap(p, st.st_size);
close(fd);

2.3 参数速查

参数常用值
protPROT_READ / PROT_WRITE / PROT_EXEC / PROT_NONE
flagsMAP_SHARED（改动写回文件、进程间可见）
MAP_PRIVATE（写时复制，改动只自己看得见）
MAP_ANONYMOUS（不关联文件，纯要内存）
MAP_POPULATE（预先加载所有页）
MAP_HUGETLB（用 2MB 大页）

配套：munmap() 解除，msync() 强制刷盘，madvise() 给内核提示访问模式。

2.4 四大用途

用途说明
① 大文件随机访问行情历史数据、数据库文件；只有真正访问到的页才加载
② 进程间共享内存MAP_SHARED + shm_open，两进程映射同一块 → 零拷贝 IPC，行情分发的标配
③ malloc 大块内存glibc 中 >128KB 的分配（M_MMAP_THRESHOLD）直接走 mmap 匿名映射
④ 加载可执行文件和动态库你的程序本身就是被 mmap 进内存的

2.5 坑（面试爱问）

坑说明
缺页中断不可控第一次访问某页会触发 page fault 陷内核，几微秒的延迟随机出现。低延迟系统必须 MAP_POPULATE 或启动时主动 touch 一遍预热
SIGBUS映射后文件被 truncate 截断，访问超出部分 → SIGBUS 崩溃
小文件不划算建立映射要改页表、刷 TLB，比一次 read 还贵
顺序流式读未必更快内核 readahead 预读对 read 很友好，mmap 反而可能更慢
写回时机不确定MAP_SHARED 的脏页何时落盘由内核决定，要确定性得 msync

2.6 全内存交易柜台里的典型用法

// 启动时：申请大页 + 预先填充 + 锁住不换出
void* p = mmap(nullptr, SIZE, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS | MAP_POPULATE | MAP_HUGETLB,
               -1, 0);
mlock(p, SIZE);       // 锁定物理内存，绝不 swap 出去

// 之后所有订单对象都从这块内存里分配（配合内存池）
// → 运行期零缺页、零 swap、延迟稳定
面试一句话

mmap 把文件或匿名内存映射进进程地址空间，省掉 page cache 到用户缓冲区的那次拷贝和反复的系统调用；代价是缺页中断的延迟不可控，所以低延迟场景要配 MAP_POPULATE + mlock 预热锁定。

3. 信号 · 有人在你干活时拍你肩膀

形象比喻

你正在专心写代码（进程正常执行）→ 突然有人拍你肩膀说「电话！」（信号到达）→ 你立刻放下手头的事去接电话（跳转到信号处理函数）→ 接完回来，从刚才断的地方继续。

关键性质：异步、随时可能发生、打断的位置完全不可预测（可能正好在你 malloc 到一半的时候）。这是理解「handler 为什么限制这么多」的钥匙。

3.1 常见信号表

信号编号触发原因默认行为
SIGSEGV11段错误：访问非法内存终止 + core
SIGABRT6abort()、未捕获异常、assert 失败终止 + core
SIGBUS7总线错误：未对齐访问、mmap 越界终止 + core
SIGFPE8算术错误：整数除零终止 + core
SIGPIPE13往已关闭的连接写数据终止（无 core）
SIGTERM15kill pid（优雅退出请求）终止
SIGINT2Ctrl+C终止
SIGKILL9kill -9、OOM Killer终止，不可捕获、不可忽略
SIGSTOP19暂停暂停，不可捕获
SIGCHLD17子进程结束忽略
SIGHUP1终端断开 / 习惯用于重载配置终止
SIGUSR1/SIGUSR210/12用户自定义终止
记牢两个

SIGKILL 和 SIGSTOP 永远无法被捕获或忽略 —— 这是内核留给管理员的最后手段，也是为什么被 OOM Killer 杀掉的进程没有任何机会做清理、也不会留下 core。

3.2 最大的坑：handler 里几乎什么都不能做

易踩坑 
void handler(int sig) {
    printf("caught %d\n", sig);      // ✗ printf 不是异步信号安全的
    std::string s = "log";           // ✗ 会 malloc
    mtx.lock();                      // ✗ 若被打断时正好持有这把锁 → 死锁
    logger.write(...);               // ✗ 同上
}

为什么：信号可能在任意指令处打断你，包括 malloc 正在改链表的中途。此时你在 handler 里又调 malloc，链表就彻底坏了。只能调用异步信号安全（async-signal-safe）的函数，白名单很短：write、_exit、signal、kill、sigaction、read 等（man 7 signal-safety）。

3.3 四种正确姿势

① 只设标志位（最简单）

volatile sig_atomic_t g_running = 1;

void handler(int) { g_running = 0; }    // 只做这一件事

int main() {
    signal(SIGTERM, handler);
    while (g_running) {                  // 在主循环里检查
        doWork();
    }
    cleanup();                           // ✓ 在正常上下文里做清理
}

volatile sig_atomic_t 是标准保证「读写原子、不会被优化掉」的唯一类型。

② self-pipe trick（能配合 epoll）

int pipefd[2];   // 启动时 pipe(pipefd)，设为非阻塞

void handler(int sig) {
    char c = (char)sig;
    write(pipefd[1], &c, 1);        // ✓ write 是安全的
}
// 主循环用 epoll 同时监听 pipefd[0] 和业务 socket
// → 信号被"转换"成了一个普通的可读事件

③ signalfd（Linux 专属，最优雅）

sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, nullptr);   // 先阻塞默认处理

int sfd = signalfd(-1, &mask, 0);          // 信号变成一个 fd
epoll_ctl(epfd, EPOLL_CTL_ADD, sfd, &ev);  // 直接丢进 epoll
// 读这个 fd 就能拿到 signalfd_siginfo，完全在正常上下文里处理

④ 专用信号线程（多线程程序推荐）

// 主线程：阻塞所有信号（新建的线程会继承这个 mask）
pthread_sigmask(SIG_BLOCK, &mask, nullptr);

// 专门开一个线程同步等信号
std::thread([mask]{
    int sig;
    sigwait(&mask, &sig);      // 阻塞等待，不是 handler，随便写什么都行
    handleGracefulShutdown(sig);
});

因为信号是发给整个进程的，默认会随机挑一个没阻塞它的线程来处理，行为不确定。

3.4 SIGPIPE：网络编程必踩

易踩坑

对端关闭连接后，你继续 write → 内核发 SIGPIPE → 默认直接终止进程。服务器就这么莫名其妙没了。

signal(SIGPIPE, SIG_IGN);                   // ✓ 全局忽略，write 返回 -1/EPIPE
send(fd, buf, len, MSG_NOSIGNAL);           // ✓ 或者单次调用屏蔽

3.5 signal vs sigaction

用 sigaction，别用 signal：后者在不同系统上语义不一致（是否自动重置 handler、是否自动重启被打断的系统调用都不确定）。

struct sigaction sa{};
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;        // 被打断的慢系统调用自动重启
sigaction(SIGTERM, &sa, nullptr);
面试一句话

信号是异步打断，可能停在任意指令上，所以 handler 里只能调异步信号安全函数，绝不能 malloc/printf/加锁。工程做法是 handler 只设 volatile sig_atomic_t 标志或 write 一个字节，真正的处理放回主循环；多线程用 signalfd 或专用 sigwait 线程。

4. core dump · 飞机的黑匣子

形象比喻

进程崩溃的那一瞬间，内核把它的内存镜像 + 寄存器 + 调用栈 + 线程状态整个 dump 成一个文件 —— 相当于案发现场被整个封存下来，包括每个人当时站在哪、手里拿着什么。你可以事后用 gdb 走进这个「凝固的现场」慢慢勘察。

哪些信号会产生 core：SIGSEGV、SIGABRT、SIGBUS、SIGFPE、SIGILL、SIGQUIT。

注意

SIGKILL（包括 OOM Killer）不产生 core —— 所以「进程没了但没有 core」通常就是被 kill -9 或 OOM 了。

4.1 开启

ulimit -c unlimited                       # 当前 shell 生效（默认往往是 0）
# 永久：/etc/security/limits.conf 里写 * soft core unlimited

# 控制生成路径和文件名
cat /proc/sys/kernel/core_pattern
echo "/var/cores/core.%e.%p.%t" > /proc/sys/kernel/core_pattern
#   %e=程序名  %p=pid  %t=时间戳  %s=信号  %h=主机名

编译时必须带 -g。Release 版本也应该 -O2 -g（调试信息不影响运行速度，只是文件变大），千万不要 strip。

4.2 gdb 分析的黄金命令序列

gdb ./my_server /var/cores/core.my_server.1234.1700000000

bt                        # ← 第一件事：看崩在哪个调用栈
bt full                   # 带上每一帧的局部变量
info threads              # 有几个线程，崩的是哪个
thread apply all bt       # ★ 所有线程的栈 —— 查死锁/并发问题必用

frame 2                   # 切到第 2 帧
info locals               # 这一帧的局部变量
info args                 # 参数
p order                   # 打印变量
p *ptr                    # 解引用看内容

x/16xb ptr                # 按字节看内存
info registers            # 寄存器
disassemble               # 汇编（优化后代码对不上行号时用）

4.3 崩溃现象 → 原因速查

现象常见原因
bt 显示地址是 0x0 附近空指针解引用
地址是很小的数（如 0x8）空指针访问成员（0x8 = 第二个字段的偏移）
栈里全是 ?? 或乱码栈被写坏（数组越界、栈溢出）；用 -fsanitize=address 复现
free(): invalid pointer / double free重复释放、释放非堆指针、堆越界写坏了元数据
崩在 std::string / vector 内部多半是用了已析构的对象或迭代器失效
崩在 pthread_mutex_lock锁对象已被销毁，或对象已释放
bt 只有一帧、无栈栈溢出（无限递归）或 -fomit-frame-pointer

4.4 大内存进程的问题

全内存柜台可能占几十 GB，dump 一次要写几十 GB，磁盘和时间都扛不住。

# 方案1：core_pattern 走管道，边生成边压缩
echo "|/usr/bin/gzip -1 > /var/cores/core-%e-%p.gz" > /proc/sys/kernel/core_pattern

# 方案2：排除不需要的内存段（比如巨大的数据缓存）
echo 0x33 > /proc/self/coredump_filter
# 或者代码里对特定区域调 madvise(addr, len, MADV_DONTDUMP)
面试一句话

core 是崩溃瞬间的进程内存快照。要能用得先 ulimit -c unlimited + 编译带 -g 不 strip；分析时先 bt 看栈，再 thread apply all bt 看所有线程，配合 info locals/p 定位。被 kill -9 和 OOM Killer 杀掉不会有 core。

5. OOM · 救生艇超载，直接扔人

5.1 先理解 overcommit：malloc 成功是一张空头支票

void* p = malloc(100L * 1024 * 1024 * 1024);   // 申请 100GB
if (p) { /* 居然成功了！机器只有 16GB */ }

memset(p, 0, ...);   // ← 真正写的时候才崩

理由是大多数程序申请了内存并不会全用（比如 fork 之后的写时复制）。后果：内存真的不够时，不是 malloc 返回 NULL，而是运行到一半突然被杀。

cat /proc/sys/vm/overcommit_memory
#  0 = 启发式判断（默认）
#  1 = 永远答应
#  2 = 严格模式：超过 swap + RAM*overcommit_ratio 就直接失败（此时才会 bad_alloc）

5.2 OOM Killer

形象比喻

救生艇超载了，船长必须扔一个人下去保住其他人。扔谁？按「评分」选 —— 谁占的地方最大、谁最不重要，就扔谁。

评分规则（oom_score）大致是：占用内存越多分越高，再叠加 oom_score_adj 的人工修正。

cat /proc/<pid>/oom_score          # 当前评分
cat /proc/<pid>/oom_score_adj      # 人工调整：-1000 ~ +1000

echo -1000 > /proc/<pid>/oom_score_adj   # -1000 = 永不被杀（谨慎使用）
echo 1000  > /proc/<pid>/oom_score_adj   # 优先杀我（适合可重启的辅助进程）

被选中的进程收到 SIGKILL —— 捕获不了、清理不了、没有 core。

5.3 怎么确认「我是被 OOM 杀的」

dmesg -T | grep -i -E "killed process|out of memory"
# Out of memory: Killed process 12345 (my_server) total-vm:... anon-rss:...

journalctl -k | grep -i oom              # systemd 系统
cat /var/log/messages | grep -i oom      # 老系统

# 容器里
cat /sys/fs/cgroup/memory/memory.failcnt
dmesg | grep -i "memory cgroup out of memory"

症状特征：进程「无声无息就没了」，日志没有任何异常，也没有 core 文件 —— 这就是典型的 OOM 或 kill -9。

5.4 三种「内存不够」要分清（高频追问）

现象原因表现
std::bad_alloc分配器要不到虚拟地址空间（32 位耗尽 / overcommit=2 / 超 ulimit -v）能捕获，程序有机会优雅处理
OOM Killer整机物理内存 + swap 耗尽SIGKILL，无 core，dmesg 有记录
cgroup OOM容器超过 memory.limit_in_bytes只杀容器内进程，宿主机没事
容器场景特别注意

容器里的进程看到的 /proc/meminfo 是宿主机的，所以你的程序以为有 128GB，其实 limit 只给了 2GB —— JVM、Go 和自己写的内存池都容易在这栽跟头。

5.5 生产环境怎么防

措施说明
启动时预分配 + mlockall一次性把要用的内存申请好、写一遍（touch）、锁住不换出，避免运行期才发现不够
关掉 swap低延迟系统必做，swap 一旦发生延迟就是毫秒级
监控 RSS 而不是 VSZVSZ 是虚拟地址（含没用的欠条），RSS 才是真实占用的物理内存
设置 oom_score_adj核心交易进程调低，辅助进程调高
cgroup 限额 + 告警提前在 80% 就告警，别等被杀
排查内存增长valgrind --leak-check=full、-fsanitize=address、heaptrack、pmap -x <pid>
面试一句话

Linux 默认 overcommit，malloc 成功只是拿到虚拟地址的欠条，第一次写才真正分配物理页；所以内存耗尽时表现为运行中被 OOM Killer 用 SIGKILL 杀掉，而不是 malloc 返回失败。因为是 SIGKILL，所以无法捕获、没有 core，只能靠 dmesg 确认。

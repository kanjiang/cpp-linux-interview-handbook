1. 内存对齐 · 停车位要画线

形象比喻

CPU 读内存不是「你要几个字节就读几个字节」，而是按固定大小的块整块搬（通常 4 或 8 字节，一条 cache line 是 64 字节）。内存被划成一格一格的停车位，一辆车正好停进一格就一次读完；横跨两格就得读两次再拼起来。

1.1 不对齐的后果

  • x86 上：能读，但慢（两次访存 + 拼接）
  • 老 ARM / SPARC / MIPS 上：直接 SIGBUS 崩溃
  • std::atomic：未对齐就无法保证原子性（原子指令要求单次访存完成）

1.2 结构体 padding：成员顺序决定大小

struct A {          // sizeof = 12
    char  a;        // 偏移 0
    // 3 字节填充    ← 为了让 b 落在 4 的倍数
    int   b;        // 偏移 4
    char  c;        // 偏移 8
    // 3 字节填充    ← 整体大小要是 4 的倍数（数组里下一个也要对齐）
};

struct B {          // sizeof = 8  ← 只是换了个顺序，省了 33%
    char  a;        // 偏移 0
    char  c;        // 偏移 1
    // 2 字节填充
    int   b;        // 偏移 4
};
规则说明
成员偏移必须是 alignof(成员类型) 的倍数
整体大小必须是最大成员对齐值的倍数（保证数组里每个元素都对齐）
实践口诀

成员按大小从大到小排（double → int64 → int → short → char → bool），能显著减少 padding。订单结构体一个字段的顺序差异，在百万级对象时就是几十 MB 的内存差。

1.3 相关工具

alignof(int);              // 4
alignof(double);           // 8
alignof(std::max_align_t); // 通常 16

alignas(64) int counter;   // 强制对齐到 64 字节（cache line）

#pragma pack(1)            // 取消填充，紧凑排列
struct Packet { char type; int len; };   // sizeof = 5
#pragma pack()
注意

#pragma pack(1) 只该用在网络协议 / 文件格式的解析结构体上（因为对端就是紧凑排列的），业务结构体用了会拖慢访问速度。

面试一句话

为什么 sizeof(struct{char; int;}) 是 8 不是 5？因为 int 必须落在 4 的倍数地址上，中间填了 3 字节；这是为了让 CPU 一次访存就能取到，避免跨边界的两次读取（某些架构上甚至直接崩）。

2. Cache 伪共享 · 两个人抢同一块白板

形象比喻

CPU 的 cache 不是按字节管理的，是按「行」管理的，一行 64 字节。办公室里有一块白板（cache line），甲要在左上角写字，乙要在右下角写字。虽然两人写的是完全不同的位置，但规则是：谁要写，就得把整块白板搬到自己桌上，别人手里的副本作废。结果白板在两张桌子之间来回飞，谁都没干成活。

伪共享（false sharing）：两个线程访问的是不同的变量，但这两个变量恰好落在同一条 cache line 上，于是在硬件层面被迫互相争抢。

2.1 代码演示

struct Counters {
    long a;   // 线程 1 只碰 a
    long b;   // 线程 2 只碰 b
};            // a 和 b 挨在一起，必定在同一条 cache line

Counters c;
// 线程1：for (...) ++c.a;
// 线程2：for (...) ++c.b;

逻辑上零冲突，实测可能比单线程还慢 5～10 倍。底层原因是 MESI 缓存一致性协议：

2.2 解决办法：把它们隔开

struct alignas(64) PaddedCounter {
    long value;
    // 编译器自动补足到 64 字节
};

PaddedCounter a, b;   // 各占一条独立的 cache line，互不打扰

C++17 提供了标准常量，不用硬编码 64：

#include <new>

struct Counters {
    alignas(std::hardware_destructive_interference_size) long a;
    alignas(std::hardware_destructive_interference_size) long b;
};
  • hardware_destructive_interference_size：要分开的最小距离（避免伪共享）
  • hardware_constructive_interference_size：要凑近的最大距离（希望一起被加载）

2.3 哪些场景要警惕

场景说明
每线程统计计数器数组long counts[NUM_THREADS] —— 最经典的翻车现场
无锁队列的 head / tail生产者写 tail、消费者写 head，必须分开
线程池的任务计数多个 worker 各自的状态字段
自旋锁数组多个锁挤在一起

2.4 真共享 vs 伪共享

现象解法
真共享多线程真的在读写同一个变量改算法：分片累加、thread_local 后汇总
伪共享变量不同，只是物理上挨着加 padding / alignas(64)
面试一句话

伪共享是「逻辑上不冲突、物理上冲突」—— 变量落在同一条 64 字节 cache line 上，一个核写就让别的核的副本失效，导致缓存行在核间来回搬运。解法是 alignas(64) 把热点变量各自隔到独立 cache line。

3. 内存池 · 自带一箱零钱，不用每次跑银行

3.1 为什么需要：new / malloc 慢在哪

1. 要在空闲链表（bins）里【找】一块合适的 2. 多线程下要【加锁】（glibc 用 arena 缓解，但仍有竞争） 3. 块不够大时要向内核要内存 → brk / mmap 【系统调用】 4. 长期运行后产生【碎片】，找块越来越慢 5. 最要命的：延迟【不可预测】—— 平时 50ns，偶尔 50μs

最后一条是低延迟系统的死穴。交易柜台不怕平均慢，怕的是尾延迟（P99.9）突然抖一下，而 malloc 恰好是抖动的主要来源之一。

形象比喻

不用内存池：每次买东西都跑一趟银行取钱（每次 new 都找分配器要）。
用内存池：开工前一次性取一万块零钱放抽屉里，要用就从抽屉拿，用完扔回抽屉，全程不出门。

3.2 最简单的实现：固定大小对象池

核心技巧：空闲块自己存下一个空闲块的地址（侵入式链表），所以额外开销为 0。

class OrderPool {
public:
    explicit OrderPool(size_t n) {
        chunk_ = static_cast<Order*>(::operator new(n * sizeof(Order)));
        // 把所有块串成一条 free list
        for (size_t i = 0; i < n - 1; ++i)
            *reinterpret_cast<void**>(&chunk_[i]) = &chunk_[i + 1];
        *reinterpret_cast<void**>(&chunk_[n - 1]) = nullptr;
        freeList_ = chunk_;
    }

    void* allocate() {
        if (!freeList_) return nullptr;                     // 池空了
        void* p = freeList_;
        freeList_ = *reinterpret_cast<void**>(freeList_);   // 摘下头节点
        return p;                                            // O(1)，无查找、无锁
    }

    void deallocate(void* p) {
        *reinterpret_cast<void**>(p) = freeList_;           // 挂回头部
        freeList_ = static_cast<Order*>(p);                  // O(1)
    }

private:
    Order* chunk_;
    void*  freeList_;
};

配合 placement new 使用（在已有内存上构造对象）：

void* mem = pool.allocate();
Order* o = new (mem) Order(id, price);   // 只构造，不分配

o->~Order();                              // 只析构，不释放
pool.deallocate(mem);

3.3 常见的池类型

类型适用说明
固定块池 / 对象池同一种对象反复创建销毁（订单、消息）上面那种，最快
Slab多种固定尺寸按 size class 分成多个池（tcmalloc 思路）
Buddy 伙伴系统变长，需要合并Linux 内核用它管物理页
Arena / 线性分配器一批对象同生共死（一次请求的临时数据）只有 alloc 没有 free，处理完整块重置，快到离谱

3.4 C++17 标准方案：std::pmr

#include <memory_resource>

char buffer[1 << 20];                                   // 1MB 缓冲
std::pmr::monotonic_buffer_resource pool(buffer, sizeof(buffer));

std::pmr::vector<int> v(&pool);      // 这个 vector 的所有分配都走 pool
v.push_back(1);                       // 零 malloc
// pool 析构时整块一起还，不逐个 free
资源类型特点
monotonic_buffer_resource只分配不回收，销毁时整体释放 —— 最快
unsynchronized_pool_resource按 size class 分池，单线程
synchronized_pool_resource同上，加锁版

3.5 坑

坑说明
线程安全加锁就失去了意义 → 用 thread_local 池，每个线程一个
跨线程释放A 分配、B 释放 → 要么用无锁队列还回去，要么设计上禁止
不还给操作系统池占的内存一直不释放，RSS 只涨不跌，容易被误判为泄漏
越界写写坏了 free list，下次 allocate 返回野指针，极难查
对齐自己管内存就要自己保证 alignof(T)
过早优化先 profile 确认 malloc 真是瓶颈，否则纯属自找麻烦
面试一句话

内存池把「频繁向系统申请/释放」变成「一次性大块申请 + 内部 O(1) 的链表摘挂」，主要收益不是平均更快，而是消除了尾延迟抖动和碎片。代价是内存不还给 OS、跨线程要额外设计、越界破坏难排查。

4.2 deque：最容易被问倒的那个

很多人以为 deque 是「双向链表」，其实是分段数组 + 一个指针数组做索引：

  • 两端插入删除 O(1)（在头/尾的块里操作，不够就再挂一块）
  • [] 随机访问 O(1)（先算第几块，再算块内偏移，比 vector 稍慢）
  • 两端插入不会让已有元素的指针/引用失效（元素不搬家），但迭代器会失效（中控可能重新分配）
  • 中间插入 O(n)

这就是 std::queue / std::stack 默认用 deque 而不是 vector 的原因：需要头部 O(1) 操作。

4.3 map / set：红黑树

红黑树五条性质： 1. 每个节点是红或黑 2. 根是黑的 3. 叶子（NIL）是黑的 4. 红节点的孩子必须是黑的（不能有连续两个红） 5. 从任一节点到其所有叶子的路径上，黑节点数量相同 → 由此保证：最长路径 ≤ 2 × 最短路径 → 树高 O(log n)
AVL红黑树
平衡程度更严格（高度差 ≤ 1）较宽松
查找略快略慢
插入/删除的旋转次数可能 O(log n) 次最多 3 次
适用查多改少增删改查都频繁 ← STL 的定位
关键性质

map/set 的元素不会移动，所以除了被删除的那个，所有迭代器、指针、引用在插入删除后都保持有效。这是它相对 vector 的一大优势。

4.4 unordered_map：哈希桶 + 链地址法

m.bucket_count();       // 桶的数量
m.load_factor();        // = size / bucket_count（平均每桶几个元素）
m.max_load_factor();    // 默认 1.0，超过就 rehash
m.reserve(n);           // ★ 预留，避免多次 rehash
rehash 的影响（考点）

迭代器全部失效，但指针 / 引用仍然有效（节点没搬家，只是重新挂到新桶上）。这和 vector 扩容不一样，vector 是连指针引用一起废掉。

需求选
需要有序遍历 / 范围查询（lower_bound）map
纯粹按 key 查，数据量大unordered_map
数据量很小（几十个）map 甚至 vector + 线性查找可能更快（cache 友好，没有 hash 计算）
要求最坏情况延迟稳定map（O(log n) 有保证；unordered_map 遇到 rehash 或碰撞会抖）

最后一条对交易系统很重要：unordered_map 的平均 O(1) 很香，但 rehash 那一下是不可预测的长尾。热路径上要么提前 reserve 到位，要么用 map，要么自己写定长哈希表。

// 关联容器删除的经典安全写法
for (auto it = m.begin(); it != m.end(); ) {
    if (shouldRemove(it->second))
        it = m.erase(it);      // ✓ C++11 起 erase 返回下一个迭代器

}

4.6 内存开销直觉

存 100 万个 int： vector<int> ≈ 4 MB ← 只有数据 list<int> ≈ 32 MB ← 每节点 2 指针 + int + 分配器开销 set<int> ≈ 48 MB ← 每节点 3 指针 + 颜色 + int + 开销 unordered_set<int> ≈ 24 MB ← 桶数组 + 每节点 1 指针

差 8～12 倍。再加上 vector 的 cache 友好性，遍历速度能差一个数量级。所以那条老规矩仍然成立：不确定用什么容器时，先用 vector。

4.7 常见追问

问题答案
push_back 为什么是「摊还 O(1)」2 倍扩容下 n 次插入的总搬迁是 1+2+4+...+n ≈ 2n，摊到每次就是常数
vector 扩容用移动还是拷贝只有元素的移动构造标了 noexcept 才用移动，否则为强异常安全只能拷贝（std::move_if_noexcept）
unordered_map 一定比 map 快吗不一定。小数据量时 map cache 局部性更好；哈希有计算开销，rehash 带来长尾；需要有序时 map 无可替代
std::sort 用什么算法introsort：快排为主，递归过深切堆排（避免最坏 O(n²)），小区间用插入排序收尾
std::list::sort 为什么不能用 std::sortstd::sort 要求随机访问迭代器，list 只有双向迭代器，所以自带归并排序成员函数

1. 什么叫互斥量（形象版）

一句话

互斥量（mutex）＝ 只有一把钥匙的门锁。谁拿到钥匙谁进屋，其他人在门口排队等。名字来自 mutual exclusion（互相排斥）。

形象比喻：机场的单人卫生间

① 甲走过去，门开着 → 进去，反锁（lock()）；② 乙走过来，门锁着 → 在门口等（阻塞）；③ 甲办完事，开锁出来（unlock()）；④ 乙进去，反锁……

┌─────────────┐ │ 卫生间 │ ← 共享数据（同一时刻只能一个人用） │ (共享数据) │ └──────┬──────┘ │ 🔒 门锁 ← mutex │ 😀 😐 😑 😠 ← 排队的线程
现实代码
卫生间共享数据（balance、queue、map…）
门锁std::mutex
反锁进门mtx.lock()
开锁出门mtx.unlock()
在门口等线程阻塞
门里的那段时间临界区

1.1 不加锁会怎样？count++ 的真相

你以为 count++ 是一步，其实 CPU 要做三步：读进寄存器 → 加 1 → 写回内存。两个线程同时执行时可能这样交错：

初始 count = 100 时间 → 线程A: 读到100 ┄┄┄┄┄┄┄┄┄ 改成101 写回101 线程B: ┄┄┄┄┄ 读到100 改成101 ┄┄┄┄┄ 写回101 ↓ 最终 count = 101（应该是 102！）

丢了一次更新，这就是数据竞争（data race）—— 相当于两个人同时挤进同一个隔间，互相把对方的事搅黄了。加锁之后，A 的「读-改-写」三步走完之前，B 根本进不来。

1.2 最反直觉的一点：锁保护的不是数据，是「约定」

高频考点 
std::mutex mtx;
int balance = 0;

void safeAdd()   { std::lock_guard<std::mutex> lk(mtx); balance += 100; }  // 守规矩
void sneakyAdd() { balance += 100; }   // ✗ 没加锁，但编译器【一句话都不会说】

mtx 和 balance 之间没有任何语法上的绑定关系。比喻：门锁只锁得住走门的人，有人翻窗户进去，锁一点办法都没有。

所以互斥量是一个君子协定 —— 全体代码约定好「碰 balance 之前先拿 mtx」，只要有一处忘了，保护就整体失效。正确做法是把数据和锁封装进类里，让外人根本没有「翻窗户」的机会：

class Account {
public:
    void add(int n) {
        std::lock_guard<std::mutex> lk(mtx_);   // 唯一的门
        balance_ += n;
    }
    int get() const {
        std::lock_guard<std::mutex> lk(mtx_);
        return balance_;
    }
private:
    mutable std::mutex mtx_;    // const 方法里要加锁 → mutex 必须 mutable
    int balance_ = 0;           // private，外面碰不到 → 没有窗户可翻
};

一份数据配一把锁，并且写在一起 —— 这是使用互斥量的第一原则。

1.3 第二个关键性质：所有权（谁锁谁开）

// 线程A
mtx.lock();
// 线程B
mtx.unlock();   // ✗ 未定义行为！B 没锁过，凭什么解锁

比喻：钥匙在甲手里，乙不能替甲开门。推论是同一个线程重复上锁会把自己锁死 —— 你在卫生间里，又想进这个卫生间一次，等于在等你自己出来。真需要重入就用 std::recursive_mutex（但通常说明设计有问题）。

1.4 为什么要用 lock_guard 而不是手动 lock/unlock

void bad() {
    mtx.lock();
    if (x < 0) return;      // ✗ 提前 return，忘了解锁 → 全场卡死
    doSomething();          // ✗ 这里抛异常，也永远解不了锁
    mtx.unlock();
}

void good() {
    std::lock_guard<std::mutex> lk(mtx);   // 构造 = 锁门
    if (x < 0) return;                     // ✓ lk 析构，自动解锁
    doSomething();                         // ✓ 抛异常栈展开，也自动解锁
}                                          // ✓ 正常结束，自动解锁

手动版的比喻：你进了卫生间，突然接到电话从窗户跑了，门还反锁着 —— 后面所有人永远进不去。RAII 相当于给门装了自动闭合弹簧。

1.5 常见误区澄清

误解真相
加了锁数据就安全了只有所有访问路径都加锁才安全，漏一处等于没加
锁保护的是变量锁保护的是一段代码（临界区），和变量靠约定关联
锁越多越安全多把锁 + 不同顺序＝死锁；锁范围过大＝性能崩
lock 失败会返回错误lock() 不会失败，只会一直等；想不等用 try_lock()
读数据不用加锁只要有人写，读也必须加锁，否则可能读到「半个」值

2. 临界区的起点和终点怎么定

结论

临界区不是语言给你的，编译器也不知道它在哪 —— 是你自己划的。依据只有一条：从「共享数据的不变量被破坏」开始，到「不变量重新成立」结束。

2.1 代码层面：边界看得见

void deposit(int n) {
    std::lock_guard<std::mutex> lk(mtx);   // ← 临界区开始（构造 = lock）
    balance += n;
}                                          // ← 临界区结束（析构 = unlock）

lock_guard 的生命周期 = 临界区范围。想精确控制边界，就用花括号显式框出来：

void handleOrder(const Order& o) {
    auto msg = parse(o);          // 不碰共享数据，在锁外

    {
        std::lock_guard<std::mutex> lk(mtx);
        orderTable[o.id] = msg;   // ← 只有这一行碰共享数据
    }                             // ← 锁在这里就放掉了

    sendToExchange(msg);          // 耗时 I/O，绝不能在锁里
}

不加这对花括号，锁会一直持有到函数结尾，把 sendToExchange 这种慢操作也圈进去 —— 功能正确，但吞吐会崩。

2.2 逻辑层面：哪些代码该进去

第 1 步：找出「共享 + 可变」的数据。三个条件同时满足才需要保护：会被多个线程访问、至少有一个线程写、不是原子操作。只读常量、线程私有的局部变量、thread_local 都不需要锁。

第 2 步：找出「不变量」（invariant），也就是「这份数据在正常状态下必须成立的性质」。比如双向链表的不变量是「每个节点的 next->prev == 自己」：

newNode->next = cur->next;
newNode->prev = cur;
cur->next->prev = newNode;   // ← 这几步中间，不变量是【被破坏】的
cur->next = newNode;         // ← 到这里才恢复

临界区必须完整覆盖「破坏 → 恢复」的整个过程。此时若别的线程闯进来遍历链表，看到的就是一个断裂的结构。这个标准比「哪一行写了变量」更本质。

2.3 划错的两种典型错误

错误 A：划太小 —— check-then-act 竞态 
// 错误写法
if (!queue.empty()) {          // 临界区①：检查
    auto item = queue.front();  // 临界区②：取用
    queue.pop();
}

即使 empty()、front()、pop() 每一个内部都加了锁，整体依然是错的 —— ①和②之间锁被放掉了，别的线程可能刚好把最后一个元素 pop 走，于是你对空队列调用 front()。

判据：只要一段逻辑是「先判断状态，再依据判断结果操作」，这两步之间就不能放锁。

bool tryPop(T& out) {
    std::lock_guard<std::mutex> lk(mtx);
    if (queue.empty()) return false;
    out = std::move(queue.front());
    queue.pop();
    return true;
}
错误 B：划太大 —— 性能塌方 / 死锁 
// 不好
std::lock_guard<std::mutex> lk(mtx);
auto data = table[id];
writeToDisk(data);        // 几毫秒的 I/O，全程占着锁
notifyUser(callback);     // 调用外部回调，它可能再去抢别的锁 → 死锁

// 改成
Data data;
{
    std::lock_guard<std::mutex> lk(mtx);
    data = table[id];     // 只把共享数据【拷】出来
}
writeToDisk(data);        // 锁外做慢活
notifyUser(callback);

两条硬规则：锁内不做 I/O、不做内存分配、不做长计算；锁内绝不调用用户提供的回调 / 虚函数（你不知道它会去锁什么，是死锁高发区）。

2.4 条件变量下的临界区（断开又接上）

std::unique_lock<std::mutex> lk(mtx);          // 临界区开始

cv.wait(lk, []{ return !queue.empty(); });     // 等待期间：锁被放开，别人可以进
                                               // 返回时：锁已重新持有
auto item = queue.front();                     // 临界区继续
queue.pop();

lk.unlock();                                   // 可以提前手动结束
process(item);                                 // 锁外处理

这也是 wait 必须用 unique_lock 而不能用 lock_guard 的原因 —— 它需要中途 unlock/lock 的能力，而 lock_guard 没有这些成员函数。

2.5 更好的做法：把边界封装掉

不要让调用方自己判断临界区在哪，让数据结构自己保证线程安全。接口设计原则：对外暴露的每个函数本身就是一个完整的临界区，调用方无论怎么组合都不会出竞态。

这也解释了为什么标准库不提供线程安全的 std::queue —— 因为 empty / front / pop 这套接口天生无法做到线程安全，必须重新设计接口。

实操判定流程
  1. 这段代码碰了哪些数据？逐个标记：私有的 / 只读的 / 共享可写的
  2. 共享可写的那些，用哪把锁保护？一份数据配一把明确的锁，写在注释里
  3. 数据从哪一行开始处于「中间态」，到哪一行恢复一致？这就是最小边界
  4. 有没有「先查后用」？有就必须合并进同一个临界区
  5. 边界内有没有慢操作或外部回调？有就挪出去

4. join() 之后线程是什么状态

要分成两个东西来看，这是理解的关键：

join 之前join 之后
操作系统线程正在跑 / 已跑完但未回收已彻底结束，内核资源全部回收
std::thread 对象joinable() == true变成「空壳」，joinable() == false
 
std::thread t(work);

t.join();
// 1. 阻塞【当前线程】，直到 work() 执行完毕并返回
// 2. 回收该线程的内核资源（栈、TCB 等）
// 3. 把 t 置为「不关联任何线程」的状态

assert(!t.joinable());                       // true
assert(t.get_id() == std::thread::id{});     // 变回默认构造的空 id

t = std::thread(anotherWork);   // ✓ t 这个对象还活着，可以重新赋值
t.join();
t.join();                       // ✗ 抛 std::system_error，不能 join 两次
join()detach()
当前线程阻塞等待立即返回
线程资源何时回收join 返回时，由你回收线程自己跑完时，由运行时回收
之后还能拿到结果/异常吗能（配合 future）不能，彻底失联
thread 对象状态变空壳变空壳
detach 的最大危险：悬空引用 
void bad() {
    int local = 42;
    std::thread t([&] { std::cout << local; });   // 捕获局部变量的引用
    t.detach();
}   // ✗ 函数返回，local 销毁，但线程可能还在跑 → UB

忘记 join 的解决办法：用 C++20 的 std::jthread，或自己写个 RAII 包装：

class ThreadGuard {
public:
    explicit ThreadGuard(std::thread t) : t_(std::move(t)) {}
    ~ThreadGuard() { if (t_.joinable()) t_.join(); }

    ThreadGuard(const ThreadGuard&) = delete;
    ThreadGuard& operator=(const ThreadGuard&) = delete;
private:
    std::thread t_;
};

5. 锁的家族：tag、std::lock、尝试加锁

5.1 先分清：互斥量 ≠ 锁管理器

std::unique_lock<std::mutex> l1(muA, std::defer_lock);
//                           ↑        ↑
//                        管理器名   被管理的互斥量
是什么例子
std::mutex muA互斥量本身，真正的共享资源，通常是成员或全局变量，长期存活muA、muB
std::unique_lock l1RAII 管理器，短命的栈上对象，负责在合适时机 lock/unlock muAl1、l2

顺带一提：l1 是小写字母 L 加数字 1，读作 "lock 1"，是普通变量名。C++ 标识符不能以数字开头，11 是非法的。示例代码图省事才这么写，实际建议用有意义的名字如 lockAccount。

5.2 三个 tag

tag含义
不传构造时立即加锁（阻塞直到拿到）
std::defer_lock先不加锁，只接管管理权，之后手动 lock()
std::try_to_lock尝试加锁，失败也不阻塞，用 owns_lock() 查结果
std::adopt_lock「我已经在外面加过锁了」，你只管负责解锁

defer_lock 的主要用途就是配合 std::lock —— 因为 std::lock 需要自己控制加锁顺序，所以构造时必须先别锁上。

5.3 std::lock 怎么避免死锁

死锁是怎么来的： // 线程 A // 线程 B lock(muA); lock(muB); lock(muB); ← 卡住 lock(muA); ← 卡住 两边各持有一把、各等对方一把，永久互等。

标准只规定 std::lock「用一种避免死锁的算法」，实现上典型是「全有或全无 + 回退重试」：

1. 阻塞式锁住第 1 把 2. 对剩下的逐个 try_lock 3. 只要有一把 try_lock 失败： → 把已经拿到的【全部释放】 → 以刚才失败的那把作为新的「第 1 把」，回到步骤 1 4. 全部拿到 → 返回

关键在于失败时立刻全部放手，不会「攥着一把等另一把」，所以不会形成循环等待。

std::unique_lock<std::mutex> l1(muA, std::defer_lock);
std::unique_lock<std::mutex> l2(muB, std::defer_lock);
std::lock(l1, l2);      // 要么两把都拿到，要么一直重试，绝不死锁

// C++17 之后：一行搞定，内部就是 std::lock，且自动 RAII
std::scoped_lock lk(muA, muB);
选择建议

新代码优先用 scoped_lock，只有需要 defer / try / 手动 unlock / 配合条件变量这些灵活能力时才用 unique_lock。

5.4 「尝试加锁」的几种写法

写法行为返回值
mu.try_lock()立刻返回，不阻塞bool
unique_lock lk(mu, std::try_to_lock)同上，包了 RAII查 lk.owns_lock()
std::try_lock(l1, l2, l3)依次 try，失败就把之前的全解开-1 成功；否则返回失败者的下标（从 0 开始）
tmu.try_lock_for(100ms)带超时，需 std::timed_mutexbool
tmu.try_lock_until(tp)等到某时间点bool
 
std::unique_lock<std::mutex> lk(mu, std::try_to_lock);
if (lk.owns_lock()) {
    // 抢到了，干活
} else {
    // 没抢到，干点别的，不阻塞
}

交易系统里 try_lock 常用于「抢不到就走降级路径」，避免主线程被拖住。

6. shared_mutex 读写锁

std::shared_mutex（C++17）有两种加锁模式，所以既能配 unique_lock 也能配 shared_lock —— 这正是它的设计意图。

模式用哪个管理器底层调用语义
独占（写）unique_lock / lock_guard / scoped_locklock() / unlock()同一时刻只能有 1 个
共享（读）std::shared_locklock_shared() / unlock_shared()可以有任意多个同时进

规则：读者之间不互斥，读者和写者互斥，写者和写者互斥。

class ConfigStore {
public:
    // 读：多个线程可以同时进来
    std::string get(const std::string& k) const {
        std::shared_lock<std::shared_mutex> lk(mtx_);
        auto it = data_.find(k);
        return it == data_.end() ? "" : it->second;
    }

    // 写：独占，此时所有读者都被挡在外面
    void set(const std::string& k, std::string v) {
        std::unique_lock<std::shared_mutex> lk(mtx_);
        data_[k] = std::move(v);
    }

private:
    mutable std::shared_mutex mtx_;
    std::unordered_map<std::string, std::string> data_;
};
别无脑用（面试爱追问）
  • 内部维护读者计数，单次加解锁开销比普通 mutex 大
  • 只有「读远多于写 + 临界区足够长」时才划算；临界区很短时普通 mutex 甚至 atomic 反而更快
  • 可能有写者饥饿（读者源源不断，写者一直排不上），标准未规定公平性
  • 不能从 shared_lock 升级成 unique_lock（标准不提供，硬做会死锁）

相关类型还有 std::shared_timed_mutex（C++14，多了 try_lock_for 等超时接口）。

7. 信号量 / latch / barrier

形象比喻

信号量本质是一个带阻塞能力的计数器，像是「一叠许可证」：计数 > 0 → acquire() 立即拿走一张；计数为 0 → acquire() 阻塞，直到别人 release() 还回来一张。

#include <semaphore>

std::counting_semaphore<10> sem(3);   // 模板参数=最大可能值，构造参数=初始值

sem.acquire();     // 拿一个「许可证」，没有就等
doWork();
sem.release();     // 还回去，唤醒一个等待者
成员函数作用
acquire()阻塞获取一个
try_acquire()非阻塞尝试
try_acquire_for(dur) / try_acquire_until(tp)带超时
release(n = 1)释放 n 个，唤醒等待者
max()静态，返回最大计数

std::binary_semaphore 就是 counting_semaphore<1> 的别名。

7.1 和 mutex 最关键的区别：没有「所有权」

std::mutexsemaphore
所有权有，谁 lock 谁 unlock，别人解是 UB无，A 线程 acquire，B 线程 release 完全合法
计数只有 0/1任意 N
递归同线程重复 lock 是 UB只是继续消耗计数
用途保护临界区限流、资源池、线程间信号通知

正因为没有所有权，信号量能做 mutex 做不到的事 —— 跨线程通知。

7.2 两个典型用途

// A. 限流 / 连接池：最多 3 个线程同时访问数据库
std::counting_semaphore<3> dbSlots(3);

void query() {
    dbSlots.acquire();
    runQuery();
    dbSlots.release();
}

// B. 生产者-消费者
std::counting_semaphore<1000> items(0);   // 初始 0 个商品

void producer() {
    queue.push(x);
    items.release();       // 商品 +1，唤醒一个消费者
}
void consumer() {
    items.acquire();       // 没商品就等
    auto x = queue.pop();
}

⚠️ 注意：queue 本身还是要另配 mutex 保护，信号量只负责「有没有」的计数通知。

7.3 latch 与 barrier（C++20）

工具语义
std::latch一次性倒计时门闩，count_down() 到 0 时所有 wait() 放行，不可重置
std::barrier可重复的集合点，N 个线程都到齐才一起放行，然后自动重置进入下一轮
 
std::latch startGate(1);

// 工作线程
startGate.wait();       // 全部卡在这里
// 主线程
startGate.count_down(); // 一声令下，全部同时开跑

8. swap(other) 的用法与含义

通用含义：交换两个对象的内部状态，而且是廉价的 —— 只换指针/句柄，不做深拷贝。

std::thread t1(taskA);
std::thread t2(taskB);

t1.swap(t2);      // 或 std::swap(t1, t2);
// 现在 t1 管理着原来跑 taskB 的那个线程，t2 管理跑 taskA 的
关键理解

它交换的是「线程句柄的所有权」，不是线程本身。操作系统里那两个线程照常跑，一秒都没停，只是 C++ 对象和它们的对应关系换了一下。unique_lock、unique_ptr、shared_ptr 的 swap 同理 —— 交换的都是所有权。

为什么标准库到处都有 swap

A. 它是 noexcept 的，所以是实现「强异常安全」的基石。经典的 copy-and-swap 惯用法：

class Buffer {
public:
    Buffer& operator=(Buffer other) {   // 注意：按值传参，拷贝在这里发生
        swap(other);                     // 只交换，绝不会抛异常
        return *this;
    }                                    // other 析构，带走旧数据

    void swap(Buffer& o) noexcept {
        std::swap(data_, o.data_);
        std::swap(size_, o.size_);
    }
private:
    char* data_;
    size_t size_;
};

如果拷贝时抛异常，那是在进入函数之前发生的，*this 完全没被动过 —— 要么全成功，要么原样不变。

B. 收缩容器内存的惯用法（C++11 之前）：std::vector<int>(v).swap(v);，现在直接用 v.shrink_to_fit()。

9. std::future 是什么

一句话定义

std::future<T> 是一个「将来才会有值」的占位符，代表某个异步操作结果的读取端。

9.1 核心概念：共享状态

future 从不单独存在，它总是和一个写入端配对，两者共享一块堆上的「共享状态」：

写入端 共享状态 读取端 ┌──────────────┐ ┌───────────────┐ ┌──────────────┐ │ promise │ │ 值 or 异常 │ │ │ │ packaged_task│ ───→ │ 是否就绪 │ ───→ │ future<T> │ │ async │ │ 等待队列 │ │ │ └──────────────┘ └───────────────┘ └──────────────┘ set_value() get()
写入端适用场景
std::async(f)最省事，直接跑一个函数
std::promise<T>手动在任意时刻、任意线程里填值
std::packaged_task<F>把可调用体包起来，方便丢进线程池

9.2 成员函数

函数作用
get()阻塞直到就绪，取走结果。只能调一次
wait()只等待，不取值
wait_for(dur) / wait_until(tp)带超时，返回 future_status：ready / timeout / deferred
valid()是否还关联着共享状态
share()转成 shared_future（可多次 get、可拷贝）

9.3 三个必知细节

A. get() 只能调一次（结果是被 move 走的）：

std::future<int> f = std::async([]{ return 42; });
int a = f.get();     // OK，之后 f.valid() == false
int b = f.get();     // ✗ 抛 std::future_error

std::shared_future<int> sf = f.share();   // 想多次读就转成 shared_future

B. 异常会跨线程传递 —— 这是 future 相对裸线程的最大优势：

auto f = std::async([]{
    throw std::runtime_error("boom");
    return 1;
});

try {
    f.get();                     // 异常在这里【重新抛出】
} catch (const std::exception& e) {
    std::cout << e.what();       // boom
}

裸 std::thread 里抛出未捕获的异常会直接 std::terminate，没法传给主线程。

C. std::async 返回的 future 析构会阻塞（大坑） 
std::async(std::launch::async, longTask);   // ✗ 临时 future 立刻析构
                                            //   → 在这里【阻塞】等 longTask 跑完
                                            //   看起来是异步，实际变成了同步

auto f = std::async(std::launch::async, longTask);   // ✓ 必须用变量接住
// ... 干别的
f.get();

9.4 promise 用法

std::promise<int> p;
std::future<int> f = p.get_future();      // 先拿到读取端

std::thread t([&p] {
    try {
        p.set_value(compute());           // 填值
    } catch (...) {
        p.set_exception(std::current_exception());   // 或填异常
    }
});

int result = f.get();                     // 主线程在这里等
t.join();

10. 为什么需要 decltype

一句话

auto 会「洗掉」引用和 const，decltype 能原样保留类型；而且它能对「还没有对象的表达式」问类型。

10.1 问题一：auto 会丢引用和顶层 const

int x = 1;
const int& cr = x;

auto  a = cr;   // int         ← 引用没了，const 也没了
auto& b = cr;   // const int&  ← 得自己补 &

decltype(cr) c = x;  // const int&  ← 原样保留

写泛型代码时，你常常需要「和某个东西完全一样的类型」，不能被 decay 掉。

10.2 问题二：返回类型依赖参数类型（最初的核心动机）

template <typename T, typename U>
??? add(T a, U b) {
    return a + b;      // int+double 是 double，int+int 是 int，写不出固定类型
}

// C++11 解法：尾置返回类型
template <typename T, typename U>
auto add(T a, U b) -> decltype(a + b) {
    return a + b;
}

为什么要写在后面？因为写在前面时 a、b 还没声明，编译器不认识它们。C++14 起可以简化成 auto add(T a, U b) 让编译器推，但返回引用时仍需要 decltype(auto)。

10.3 问题三：完美转发返回值

template <typename F, typename... Args>
auto call(F&& f, Args&&... args) {
    return f(std::forward<Args>(args)...);   // ✗ f 返回 int& 时退化成 int
}

template <typename F, typename... Args>
decltype(auto) call(F&& f, Args&&... args) {
    return f(std::forward<Args>(args)...);   // ✓ f 返回什么，就原样返回什么
}

decltype(auto)（C++14）＝「按 decltype 的规则推导」，是转发层的标准写法。

10.4 问题四：在「不求值语境」里问类型

decltype(expr) 不会真的执行 expr，只分析它的类型。这在类型萃取、SFINAE、概念检测里很关键 —— 你想知道「这个调用合不合法 / 返回什么」，但不想真的调用它。

decltype(std::declval<Order>().id) n = 0;   // int，没有真的构造 Order

// 检测类型 T 是否有 size() 成员
template <typename T>
auto hasSize(int) -> decltype(std::declval<T>().size(), std::true_type{});
template <typename T>
std::false_type hasSize(...);

10.5 推导规则（三条，考点）

int x = 0;
int& rx = x;

decltype(x)     a;      // int      ← 变量名 → 它的声明类型
decltype(rx)    b = x;  // int&     ← 声明是引用就是引用
decltype((x))   c = x;  // int&     ← 加括号变成「表达式」，左值 → 加 &
decltype(x + 1) d;      // int      ← 纯右值表达式 → 不加引用
写法结果
decltype(变量名)变量声明时的类型
decltype(表达式)表达式是左值 → T&；是纯右值 → T
decltype((x))多一层括号 → 变成表达式 → int&

decltype((x)) 那个坑几乎必考。

10.6 auto vs decltype

autodecltype
依据初始化式任意表达式（可不求值）
引用默认丢弃保留
顶层 const默认丢弃保留
必须有初始值是否
典型用途局部变量少写类型泛型返回类型、类型萃取、完美转发
一句话背诵

auto 是「给我一个方便的类型」，会 decay；decltype 是「告诉我这个表达式确切是什么类型」，保留引用和 const，还能在不求值的情况下问。泛型库、返回类型推导、完美转发离不开它，业务代码里日常用 auto 就够。
